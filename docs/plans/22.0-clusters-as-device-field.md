# Plan 22.0 — M11d revised : Clusters as a Device Field

> Status: draft
> Depends on: Plans 19–21 complete. **Supersedes Plan 20 §3.1** (a cluster is no longer a saved selector).
> Blocks: nothing in the M12 series technically, but it changes `devices`, `clusters`, and every batch/schedule target path — so it lands **before** Plan 22.1 to avoid rebasing that work.
> Spec references: §7.5 (device identity), §12 (entities), §13 (protocol).

---

## 1. Goals

- Every device carries a **`cluster` field**: either empty (unclustered) or pointing at exactly one cluster.
- A device belongs to **at most one cluster**. Membership in two clusters is not expressible, at the schema level rather than by convention.
- A cluster is a **container** — a parent, a region — that devices are put into and taken out of, not a query that happens to match them.
- Existing clusters survive the change: their current members are materialised into the new field, and any device that resolved into two clusters is reported rather than silently assigned.
- Tags keep working exactly as Plan 19 defined them, for filtering and for ad-hoc batch targeting. Tags simply no longer define cluster membership.
- Every place that shows a device shows its cluster, and the devices list can filter by it.

## 2. Non-goals

- Removing tags, or changing tag semantics anywhere else. Plan 19 stands.
- Nested clusters / sub-regions. One level only; recorded in §9.
- Per-cluster permissions or ownership. The Plan 09 ACL is unchanged.
- Changing batch concurrency, ordering, or reporting — Plan 20's execution model is untouched. Only *how a cluster resolves to devices* changes.
- Changing schedules. `schedules.clusterId` keeps its meaning; it just resolves differently.

## 3. Context and design decisions

### 3.1 Why the selector model is being replaced

Plan 20 §3.1 chose a saved selector deliberately, and the reasoning was sound for the problem as stated then: devices are not moved, membership is recomputed at dispatch, and a device can be in "Android 15" and "smoke pool" at once.

The farm's actual mental model turned out to be different. A cluster is a **place** — a region, a rack, a customer — and a phone is in one place. With the selector model:

- Two clusters can silently claim the same device, so "run on cluster A" and "run on cluster B" can dispatch to the same phone at the same time.
- "Which cluster is this device in?" has no answer; it has a list of answers that changes as tags change.
- Adding a tag can move devices between clusters as a side effect, with nothing in the UI showing that it happened.

A single owning field makes the question answerable, makes the answer stable, and makes the conflict impossible instead of merely unlikely.

### 3.2 The constraint is the column, not a rule

`devices.clusterId` being a single nullable column *is* the "one cluster per device" guarantee. There is no membership table to keep consistent, no uniqueness index to enforce, and no code path that can produce a device in two clusters — assigning a device to a cluster is an `UPDATE` that necessarily removes it from any previous one.

That is the whole point of the change: the invariant is structural.

### 3.3 What happens to `clusters.tags` and `clusters.deviceIds`

Both columns are dropped. A cluster keeps only `id`, `name`, `description`, `createdAt`.

The alternative — keeping them as "default membership rules" — reintroduces exactly the ambiguity this plan removes, because a device could then be a member both by field and by rule.

### 3.4 Migrating existing clusters is lossy, so it is explicit

Existing clusters resolve to device sets that may overlap. Collapsing them into a single field must pick a winner. The rule:

1. Process clusters in `createdAt` order, oldest first.
2. For each, resolve its members with the **existing** `resolveCluster` logic (tags AND + explicit ids).
3. Assign `devices.cluster_id` only where it is still `NULL` — the oldest cluster wins.
4. Every device that matched a later cluster but was already taken is written to a migration report at `logs/cluster-migration-<timestamp>.json` and logged at `warn` with both cluster names.

Losing membership silently would be worse than the ambiguity it replaces, so the report is a required output, not a nicety. A device that matched no cluster stays `NULL`, which is the correct default.

### 3.5 Ad-hoc tag targeting survives

`resolveTarget(db, { tags, deviceIds })` stays exactly as it is. Batches and schedules can still target an ad-hoc tag set — that is a useful capability and it never claimed to be a cluster.

What changes is `resolveCluster`, which becomes a membership lookup:

```sql
SELECT * FROM devices WHERE cluster_id = ?
```

The `via` field on a resolved target gains a `'cluster'` value alongside `'tag'` and `'explicit'`, so batch reports keep saying *why* each device was picked.

### 3.6 Deleting a cluster must not delete devices

Deleting a cluster sets `cluster_id = NULL` for its members in the same transaction. The devices become unclustered; nothing else about them changes. This mirrors how Plan 19 handles tag cleanup on device delete.

## 4. Technical design

### 4.1 Schema — `packages/core/src/db/schema.ts`

```ts
export const devices = sqliteTable('devices', {
  // … existing columns …
  /**
   * The owning cluster (Plan 22.0 §3.2), or null when unclustered. A device
   * belongs to at most one cluster; this column IS that guarantee.
   */
  clusterId: text('cluster_id'),
}, (t) => [
  // … existing indexes …
  index('idx_devices_cluster').on(t.clusterId),
])

export const clusters = sqliteTable(
  'clusters',
  {
    id: text('id').primaryKey(),
    name: text('name').notNull(),
    description: text('description'),
    createdAt: integer('created_at', { mode: 'timestamp' }).notNull(),
  },
  (t) => [index('idx_clusters_created').on(t.createdAt, t.id)],
)
```

Migration generated with `bun run --cwd packages/core db:generate`. Because the data transformation in §3.4 cannot be expressed in the generated SQL, it runs as a **one-shot migration step in the core's startup path**, guarded by a marker row so it runs exactly once:

- add `devices.cluster_id` and the index (generated SQL),
- run the assignment + report (TypeScript, `packages/core/src/db/migrations/cluster-materialise.ts`),
- drop `clusters.tags` and `clusters.device_ids` (generated SQL, in a later migration file so the data step sits between them).

### 4.2 Protocol — `packages/protocol`

`DeviceInfoSchema` (`src/device.ts`) gains:

```ts
cluster: z.object({ id: z.string(), name: z.string() }).nullable().default(null),
```

An object rather than a bare id, so every list and picker can render the name without a second lookup — the same reasoning that put `tags` inline in Plan 19.

`ClusterInfoSchema` (`src/messages/batch.ts`): `tags` and `deviceIds` are removed; `deviceCount` and `usableCount` are added.

`ResolvedTarget.via` gains `'cluster'`.

### 4.3 Core — cluster membership

`packages/core/src/clusters/membership.ts` (new):

```ts
export function assignDevices(db: Db, clusterId: string, deviceIds: string[]): { moved: { deviceId: string; from: string | null }[] }
export function unassignDevices(db: Db, deviceIds: string[]): void
export function clusterMembers(db: Db, clusterId: string): DeviceRow[]
export function deleteClusterAndUnassign(db: Db, clusterId: string): void
```

`assignDevices` runs in one transaction, reports what each device moved *from* (so the API can return "3 devices moved out of Jakarta"), and rejects unknown device or cluster ids with `EnkakuError`.

`resolveCluster` in `clusters/resolve.ts` is rewritten to a membership lookup, keeping the existing `usable` / `skipped` shape and the `unavailableReason` rule unchanged — an offline member is still reported as skipped, never dropped.

### 4.4 API — `packages/core/src/api/clusters.ts` and `devices.ts`

```
PUT    /api/devices/:id/cluster        { clusterId: string | null }
POST   /api/clusters/:id/devices       { deviceIds: string[] }   → { moved: [...] }
DELETE /api/clusters/:id/devices/:deviceId
GET    /api/clusters/:id/devices       → paginated device list
GET    /api/devices?clusterId=<id|none>
```

`POST /api/clusters` and `PATCH /api/clusters/:id` drop `tags` / `deviceIds` from their bodies. `DELETE /api/clusters/:id` unassigns members (§3.6). Cluster preview (`ClusterPreviewSchema`) now previews an **ad-hoc target**, not a cluster, and is renamed accordingly in the route while keeping its shape.

All mutations require `device.manage` (the permission tag editing already uses) and are written to the audit log.

### 4.5 Studio

- **Device card and device page**: a cluster chip beside the tags; "Unclustered" rendered muted rather than omitted, so the field is visibly a field.
- **Devices list**: a cluster filter (including an explicit "Unclustered" option) alongside the existing tag filter, and optional grouping by cluster.
- **Clusters page**: each cluster shows its members with add/remove; adding a device already in another cluster shows "this will move it out of *X*" before confirming — a move is not a surprise.
- **Device picker** (`RunScriptDialog`): devices grouped by cluster, keeping the Plan 19 rule that unusable devices stay visible with a reason.
- Tailwind v4 token classes only (`bg-surface`, `text-fg-muted`), never bracket syntax.

### 4.6 Documents to update in the same commit

- `docs/plans/20-m11d-clusters-and-batch-runs.md` §3.1 — a note at the top of the section: superseded by Plan 22.0, with a one-line summary of the new model. The rest of Plan 20 (batches, concurrency, reporting) stands.
- `docs/spec.md` — if §12 describes clusters as a selector, correct it to the owning-field model.

## 6. Acceptance criteria

1. A device has exactly one `cluster` field: a cluster reference or null. No API or code path can place a device in two clusters.
2. Assigning a device that already belongs to another cluster moves it, and the response reports what it moved from.
3. Deleting a cluster unassigns its members and deletes no devices.
4. `GET /api/devices?clusterId=none` returns exactly the unclustered devices.
5. A batch targeting a cluster runs on its members; offline members appear as skipped with a reason, not dropped.
6. Batch reports show `via: 'cluster'` for devices picked by membership.
7. Migration from a database with overlapping clusters assigns oldest-first, leaves nothing double-assigned, and writes a report naming every conflict.
8. Migration is idempotent: starting the core twice does not reassign or duplicate.
9. Schedules targeting a cluster keep working unchanged.
10. `DeviceInfo.cluster` is populated in one bulk query — no N+1 on the devices list.
11. Studio shows the cluster on the card, the device page, and the picker, and warns before a move.
12. Plan 20 §3.1 carries the superseded note; the spec matches the implemented model.
13. `bun run typecheck` passes; `bun test` is green.

## 7. Test plan

**Unit:**
- `membership.test.ts` — assign, move (with the `from` report), unassign, delete-unassigns, unknown ids rejected, transactionality.
- `resolve.test.ts` — update in place: cluster resolution by membership; offline/quarantined still reported as skipped; `resolveTarget` behaviour unchanged.
- `cluster-materialise.test.ts` — an in-memory DB with three overlapping clusters: oldest wins, the report names each conflict, a second run changes nothing.
- `device-registry.test.ts` — `DeviceInfo.cluster` populated, one query for N devices.

**Manual smoke:**
```bash
bun run dev && bun run dev:studio
# 1. create clusters "Jakarta" and "Bandung"
# 2. assign a device to Jakarta → the chip appears on card and device page
# 3. assign the same device to Bandung → warned it will move; after confirming,
#    Jakarta no longer lists it
# 4. filter devices by Unclustered → the device is absent; by Bandung → present
# 5. run a batch on Bandung → it runs on its members; a powered-off member is
#    reported as skipped/offline
# 6. delete Bandung → its devices become unclustered and still exist
```

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| The migration silently drops membership someone depended on. | Oldest-wins is deterministic, every conflict is written to a JSON report and logged at `warn`, and the smoke test starts from a database with deliberate overlap. |
| Dropping `clusters.tags` loses the intent behind a cluster ("all Android 15"). | The tags themselves remain on the devices; only the cluster's copy of the rule is dropped, and the migration materialises the result before dropping anything. |
| A batch mid-flight while devices are reassigned targets a stale set. | Membership is resolved once at dispatch, exactly as before — a reassignment during a run does not retarget it. Unchanged behaviour, stated explicitly. |
| N+1 queries when loading clusters for the devices list. | Loaded in the same bulk pass as tags, with an acceptance criterion (§6.10) and a test. |
| Plan 20 and the spec drift out of date and mislead the next agent. | Step 22.0.6 updates both, with acceptance criterion §6.12. |

## 9. Open questions

1. Nested clusters (region → rack) would need a parent pointer and recursive resolution. Deliberately out of scope; the single level is what was asked for.
2. Should a cluster be able to declare a *default* tag applied to devices joining it? Convenient, but it re-couples the two concepts this plan just separated. Deferred.
3. Should `DeviceInfo.cluster` carry the description too? Currently id and name only, on the grounds that lists render a chip.
