## 0. Evidence

### 0.1 Where this comes from

The owner runs ~60 LTE modems behind a MikroTik + trunked-VLAN switch stack, one VLAN/IP per modem, and already uses plan 117's `direct` upstream (`bindAddress` = a modem's VLAN IP) to route a given proxy record's egress through one specific modem. The ask, in the owner's own words: *"ketika modem gangguan atau kuota habis... itu bisa ada sistem backup... buka suatu web ternyata error proxynya, nah kan kita gatau yang error proxy/modem kita atau webnya... makanya ini trigger suatu sistem untuk check generic web... kalau proxy itu gangguan, dengan sistem ini bisa otomatis di-routing ke backup proxy."* Two concrete requirements followed directly from that: (1) a backup upstream — another local modem, or a third-party rotating proxy (SOAX) — that a record fails over to; (2) a real modem failure must be told apart from an unrelated target-site failure before switching, or a flaky website would falsely burn through backups for no reason.

### 0.2 What already exists — confirmed by reading the code, not assumed

- **The generic-check primitive already exists and is already generic over upstream kind.** `plugins/proxy-manager/src/service/probe.ts`'s `runEgressProbe({ upstream, probeUrl, timeoutMs, secrets })` dials **the record's own `Upstream` object** (`upstream.connect({ host, port })`) to `ENKAKU_NETWORK_PROBE_URL` — the farm's own self-hosted `packages/probe-server`, plain HTTP only, `https:` refused by name (`probe.ts:29-31`, `packages/probe-server`'s own README: a third-party IP-echo site is a deliberately rejected design, plan 51 §3.3). It already works for any of `socks5`/`http`/`https`/`direct`, never throws (`{ ok, latencyMs, publicAddress?, error? }`), and is already invoked once per record per sweep from `supervisor.ts:386` (`probeEntry`). This is the exact mechanism to reuse for "is the modem itself actually down" — no new probe primitive is needed, only a new caller of the existing one.
- **No consecutive-failure counting or up/down state exists anywhere in this plugin.** `listener.ts:222-224`'s `classifyDialError`/`hooks.onFailure` fires per-connection, uncounted — a single dial failure is never accumulated into anything. `supervisor.ts`'s only comment mentioning backoff (`:196`) is about an unrelated external module (`tunnel.ts`), not this plugin's own logic.
- **`ProxyUpstream` (`shared.ts:419-`) is a single flat `interface`, not an array, not a zod schema.** `ProxyRecord` has exactly one `upstream: ProxyUpstream` field. There is no fallback/secondary field of any kind today.
- **The listener's upstream is bound ONCE, at listener-creation time, not per-connection.** `supervisor.ts:491`'s `startLocked` calls `createUpstream(entry.record, ...)` once, and the resulting object is captured in a closure (`listener.ts:183-184`'s per-connection `opts.upstream.connect(dest)` always reads the SAME object). Swapping the live upstream while the listener keeps running its port is **not supported today** — this plan has to add that, not just add a schema field.
- **A per-record, per-item alert-chip pattern already exists in Studio** (`packages/studio/src/components/guest-agent/AgentAlertChip.tsx`) — the natural precedent for a failover-state indicator, as opposed to a farm-wide banner (`AdbServerBanner`/`ProvisioningBanner`, both mounted in `AppShell.tsx`), since failover state is per-record, not farm-wide.
- **The record editor is one large component** — `plugins/proxy-manager/src/ui/parts/catalogue.tsx` is already 2320 lines and holds the upstream-editing form directly on a `local` state object (`upstream: { proto, host, port, username, bindAddress, resolveThroughEgress }`, `catalogue.tsx:266-267`). A new "backup upstreams" section belongs in its own file, not appended to this one.
- **A third-party backup (SOAX) needs no new upstream kind.** SOAX's rotating endpoints are plain HTTP/SOCKS5 with username:password auth — exactly `ProxyUpstream`'s existing `proto: 'http' | 'socks5'` shape. A fallback entry is configured the same way the primary already is; nothing new to build for this specific case.

### 0.3 Decisions already made with the owner (not to be re-litigated by whoever builds this)

- **Auto-failback default ON, per-record override.** When the active upstream is a backup and the primary later proves healthy again (background re-probe), the record switches back to primary automatically by default — the owner can turn this off per record and use a manual "reset to primary" action instead. Owner's own words: *"bisa otomatis balik, mungkin dibuatkan pengaturan aja bebas user mau pilih mana tapi defaultnya otomatis balik."*
- **Probe target is fixed, not configurable per record.** The owner chose "target tetap, tidak perlu diatur" over a per-record custom probe URL. This plan uses the existing farm-wide `ENKAKU_NETWORK_PROBE_URL` (§0.2) for this — not a new public third-party target (Google/Cloudflare, floated in the question that was asked, but the existing self-hosted probe already satisfies "fixed, not per-record" and avoids introducing a second, weaker probe path the project's own §4.3 convention warns against).

## 1. Goals

1. A `ProxyRecord` can declare an ordered list of backup upstreams (any existing `ProxyUpstream` shape — another local modem via `direct`, or a third-party service like SOAX via `http`/`socks5`), in addition to its existing primary `upstream`.
2. A real, sustained upstream failure (not a single blip, not a target-site-specific error) triggers failover to the next configured backup, confirmed by a generic probe through the SAME upstream before switching — so a flaky target website never burns through backups.
3. The listener's client-facing port never restarts during a failover — only new dials move to the new upstream; already-open connections are undisturbed.
4. Auto-failback to primary, on by default, togglable per record; a manual "reset to primary" action always available.
5. The record's current active upstream (primary vs. which backup) and its failover history are visible in Studio, following the existing per-item alert-chip pattern.

## 2. Non-goals

- A generic multi-hop proxy chain (upstream A through upstream B) — out of scope; a record dials exactly one upstream at a time, just switching WHICH one.
- Health state persisted across a core restart — deliberately in-memory only (§4.4); a restart always starts from primary and lets ordinary failure-detection re-discover if primary is still down. Persisting a stale "was on backup" pointer across a restart risks masking a since-recovered primary for no benefit.
- Per-record custom probe URLs — explicitly decided against (§0.3).
- Rewriting `runEgressProbe`/`probe.ts` — reused unchanged; this plan only adds new call sites and new state around it.
- Farm-wide health dashboards, historical uptime graphs, or alerting integrations (email/Slack/etc.) beyond the in-Studio chip and a log line — a future plan's scope if the owner wants it.

## 3. Context and design decisions

### 3.1 Why the confirmation probe runs through the SAME upstream, not a fresh check

This mirrors `runEgressProbe`'s own existing design principle (`probe.ts`'s header comment, plan 117 §3.7): probing through a DIFFERENT connection would prove nothing about whether THIS upstream is actually broken. The whole point of the confirmation step is "is the modem/upstream itself reachable at all" — answerable only by dialling out through it.

### 3.2 Why the failure counter lives per-(record, active-upstream), not per-record

If a record has already failed over to backup #2, a NEW failure streak against backup #2 must count independently from whatever streak preceded the earlier failover — otherwise a record could fail out of every configured backup in one confused burst triggered by stale counts. Switching upstream always resets the counter to zero.

### 3.3 Why the listener needs a mutable upstream holder, not a supervisor restart

Restarting the record's listener on every failover would drop the local port briefly — for an HTTP-mode bridge, that means a device's in-flight request fails exactly at the moment the plugin is trying to recover from a failure, the opposite of the goal. §0.2 already confirmed the upstream is fixed at listener-creation time; the fix is to make the listener read the ACTIVE upstream through one level of indirection (a small mutable holder object supervisor.ts owns and reassigns), so already-open connections are untouched and only the NEXT dial sees the new upstream. This is a small, surgical change, not an architecture rewrite — `listener.ts`'s per-connection dial already goes through `opts.upstream.connect(dest)`; only the thing `opts.upstream` resolves to needs to become swappable.

### 3.4 Why VPN mode is out of scope for the first cut

The failover trigger (a dial failure inside THIS plugin's own HTTP-mode bridge) has no equivalent signal in VPN mode — a `vpn-helper` route's health is reported by the guest agent's own `egress` check (`packages/core/src/network/route-checks.ts`), a completely different code path this plugin does not own. Extending failover to VPN-mode records is real, separate work; scoped here as an explicit gap (§9 Q1), not silently done or silently promised.

## 4. Technical design

### 4.1 Schema (`plugins/proxy-manager/src/shared.ts`)

- `ProxyRecord` gains `fallbackUpstreams: ProxyUpstream[]` (default `[]` on read, same read-time-default discipline plan 117 §3.1/§4.1 already established for this same KV-backed catalogue — no SQL migration, nothing to remove, matching that row's shape in `docs/plans/00-overview.md` §9).
- `ProxyRecord` gains `failover: { failureThreshold: number; autoFailback: boolean }`, defaulted on read (`failureThreshold: 3`, `autoFailback: true`) the same way. No separate "enabled" flag — failover logic is simply inert when `fallbackUpstreams` is empty (matches CLAUDE.md's "don't add fields beyond what's needed").

### 4.2 Runtime state (new file, `plugins/proxy-manager/src/service/failover.ts`)

Per live `ProxyEntry` (in-memory only, §2):
```ts
interface FailoverState {
  activeIndex: number          // 0 = primary, 1..n = fallbackUpstreams[i-1]
  consecutiveFailures: number  // against activeIndex's upstream only (§3.2)
  primaryRecoveryStreak: number // consecutive successful background primary probes, only tracked while activeIndex !== 0
  history: { at: number; from: number; to: number; reason: string }[] // bounded, most-recent-first, for the Studio chip's detail view
}
```
- On `listener.ts`'s existing per-connection `onFailure` hook: increment `consecutiveFailures` for the CURRENT `activeIndex`. On any successful dial: reset it to 0 (a live signal already exists for this — `listener.ts` already knows dial success/failure per connection, this is a new counter fed by an existing hook, not a new failure-detection path).
- When `consecutiveFailures` reaches `failover.failureThreshold`: call `runEgressProbe` (unchanged, §0.2) through the CURRENTLY active `Upstream`.
  - Probe **succeeds** → the streak was target-site-specific, not this upstream's fault (§3.1) → reset `consecutiveFailures` to 0, do not switch, do not log a warning (this is the false-positive case the whole plan exists to avoid).
  - Probe **fails** → advance `activeIndex` to the next configured fallback (wrapping is NOT done — see below), swap the listener's live upstream (§4.3), reset `consecutiveFailures`, append to `history`, emit the WS event (§4.5).
  - If `activeIndex` is already at the last configured fallback and it also fails its probe → stay there, mark the record's health as fully down, log at `warn`, still emit the WS event (naming "no working upstream left" as the reason) — cycling back to primary here would just repeat a probe already known to be failing (primary's own health is tracked independently, §4.4).

### 4.3 Swappable upstream (`supervisor.ts`, `listener.ts`)

- `startLocked` builds a `{ current: Upstream }` holder instead of handing the listener a bare `Upstream`; `listener.ts`'s per-connection dial becomes `holder.current.connect(dest)`.
- Failover (§4.2) calls `holder.current = await createUpstream(nextUpstreamRecord, ...)` — the existing `createUpstream()` (plan 117, already async, already handles the Windows/gost branch) is reused unchanged; only what gets passed to it changes (a fallback's `ProxyUpstream` instead of the primary's).
- The probe (§4.2) always dials through `holder.current` at the moment it runs, so it is always testing whatever is actually live right now.

### 4.4 Auto-failback (background primary re-probe)

- Piggybacks on the periodic sweep `supervisor.ts:413` already runs (no new timer): whenever `activeIndex !== 0` for a record, that SAME sweep tick also runs `runEgressProbe` against the PRIMARY upstream (a fresh, throwaway `Upstream` built from `record.upstream` — not `holder.current`, since primary is not the live one right now).
- On a successful primary probe: increment `primaryRecoveryStreak`; once it reaches a small fixed threshold (2, not owner-configurable — this is an internal anti-flap guard, not a product-facing setting), and only if `record.failover.autoFailback` is true: swap `holder.current` back to a freshly built primary `Upstream`, set `activeIndex = 0`, reset both streak counters, append to `history`, emit the WS event.
- On a failed primary probe: reset `primaryRecoveryStreak` to 0 — a flaky primary that comes and goes must not accumulate credit across gaps.
- When `autoFailback` is false: still run the background primary probe (so Studio can show "primary looks healthy again" as information), but never auto-switch — only the manual "reset to primary" Studio action (§4.5) sets `activeIndex = 0`.

### 4.5 Studio (plugin UI, `plugins/proxy-manager/src/ui/`)

- New file (not appended to the already-2320-line `catalogue.tsx`, §0.2) for the backup-upstreams editor: an ordered list of upstream rows (reusing the same per-kind fields `catalogue.tsx` already renders for the primary — extract that per-upstream-kind field group into a shared component both the primary editor and this one call, rather than duplicating the `direct`/`socks5`/`http`/`https` field-switch logic a second time), plus `failover.failureThreshold` and `failover.autoFailback` fields.
- A per-record chip (following `AgentAlertChip.tsx`'s pattern, §0.2) showing the current active upstream when it is NOT primary ("Aktif: Backup #2 sejak 14:32"), with a detail popover listing `history`, and a "Reset ke primary" button (always available, not just when `autoFailback` is off — an operator may want to force it back sooner than the auto-recovery streak would).
- A WS event (new type, e.g. `proxy.failover`) broadcasts `{ recordId, from, to, reason, at }` on every switch (forward or failback) — logged at `warn` (forward) / `info` (failback) in `supervisor.ts`'s own logger, and consumed by the new chip for live updates without a poll.

**121.4 — per-upstream-slot secret storage. DONE.** (Inserted after 121.3 surfaced a real gap, not in the original plan.) 121.3's own worker found and named this rather than silently guessing: `proxy-secret:<id>` (`shared.ts`) stored exactly ONE password per RECORD, and `ProxyUpstream` has no password field of its own — so a fallback built by 121.3 reused the PRIMARY's stored password, which is wrong the moment a fallback is a different account (SOAX, or a second local egress needing its own creds) rather than the same one. This step fixes that at the storage layer before the Studio editor (121.6) needs to collect per-fallback credentials.
- The secret key scheme widened from `proxy-secret:<id>` to `proxy-secret:<id>:<slot>` via new `proxySecretSlotKeyFor(id, slot)` in `shared.ts` (re-exported from `record.ts`), where `slot` is `0` for the primary upstream and `1..n` for `fallbackUpstreams[slot-1]` — mirroring `readFallbackUpstreams`' own index-based addressing from 121.1. `proxySecretKeyFor(id)` (the bare, pre-121.4 key) is unchanged and is the legacy key the new scheme falls back to, not replaced.
- **Backward compatibility, read-time, no migration script:** `supervisor.ts` gained `readSlotPassword(id, slot)`, which reads `proxy-secret:<id>:<slot>` and, for slot 0 only, falls back to the legacy bare `proxy-secret:<id>` key when the slotted row does not exist — the same "read-time default for a pre-existing shape" discipline plan 117 and 121.1 already established for this KV catalogue. Fallback slots (1..n) have no legacy key to fall back to: no secret written for a slot resolves to `''`, not a throw, not the primary's password. `supervisor.ts`'s existing `readPassword(id)` is now a thin `readSlotPassword(id, 0)` wrapper, so every other call site (the probe sweep, `startLocked`'s own primary read) is unchanged. `apply.ts`'s VPN-mode `readPassword` — a genuinely separate call site the plan text did not name, found by reading the code (§0.2 discipline) — got the identical slot-0-with-legacy-fallback treatment for the same correctness reason: VPN mode has no fallback of its own (§3.4, an explicit non-goal) so it only ever needs slot 0, but that slot's key scheme is the same one 121.4 widened, and leaving it reading only the bare key would silently break VPN-mode records the moment 121.6's editor starts writing to `:0`.
- `supervisor.ts`'s `startLocked`/121.3's `createFailoverController` wiring: `FailoverHost.buildUpstream`/`.probe` (`failover.ts`) both gained a `slot: number` parameter — the slot a build is FOR, or the slot currently active being probed — so `supervisor.ts` can call `readSlotPassword(id, slot)` for the RIGHT slot instead of closing over the primary's `password` variable. This replaces the "reuses the SAME stored password" behavior 121.3 documented as a named gap, not an addition on top of it. The confirmation probe's `secrets` (used only to scrub a password out of error text) is now the ACTIVE slot's own password too — a secrets-discipline fix beyond the plan's literal wording: leaving it pinned to the primary's password would fail to redact a fallback's own credential from an error message once a switch had happened.
- **Deviation from this step's own text:** "whatever route currently WRITES `proxy-secret:<id>` — likely in `index.ts`'s record-create/update handler" does not exist. Reading `index.ts`, `apply.ts` and `ui/parts/catalogue.tsx` (read-only, per this step's own out-of-UI-scope instruction) found the actual write path: the screen's `putSecret()` (`catalogue.tsx`) calls the CORE's generic `PUT /:name/data/entry` route (`packages/core/src/api/plugins.ts`) directly with `{ key: proxySecretKeyFor(id), value: { password }, secret: true, hint: false }` — a generic KV write endpoint shared by every plugin, not something `index.ts` (or any file in this pack's non-UI half) owns or wraps. ## 6. Acceptance criteria

1. A record with zero `fallbackUpstreams` behaves byte-for-byte as it does today — failover logic is provably inert, not merely "configured off."
2. A single, isolated dial failure (below `failureThreshold`) never triggers a confirmation probe or a switch.
3. A failure streak that reaches threshold, where a confirmation probe through the SAME upstream SUCCEEDS, does not switch — proven by a dedicated test, not merely by code inspection (this is the plan's whole reason to exist).
4. A failure streak that reaches threshold, where the confirmation probe also fails, switches to the next configured fallback, and an already-open connection through the old upstream is unaffected by the swap.
5. `autoFailback: true` (the default) switches back to primary automatically once the anti-flap recovery streak is met; `autoFailback: false` never does, leaving only the manual reset action.
6. `bun run typecheck` is clean; every touched file's own test file passes, run scoped and sequential (CLAUDE.md's hard rule).
7. `docs/plans/00-overview.md` §9 gains a row for the schema addition, matching the existing rows' format.

## 8. Risks

| Risk | Mitigation |
|---|---|
| The confirmation probe itself is slow (network round-trip to `probe-server`) and delays failover past the point where it still helps | `runEgressProbe`'s existing `timeoutMs` already bounds this (plan 117); this plan does not change that bound, only adds new callers of it |
| An operator configures a backup with wrong/expired SOAX credentials, so failover "succeeds" onto a backup that is itself broken | The SAME failure-counting logic applies to backup #2 exactly as it does to primary (§3.2) — a broken backup fails its own streak and cascades to backup #3 or "no working upstream left," it is not a dead end requiring new code |
| Auto-failback flaps a genuinely intermittent primary | The recovery-streak anti-flap guard (§4.4) plus reset-on-any-failure (not just reaching threshold) — a primary that comes and goes never accumulates partial credit |
| The shared per-kind upstream-field-group extraction (§4.5) regresses the EXISTING primary-upstream editor while refactoring `catalogue.tsx` | Per the owner's explicit no-UI-tests instruction this can't be caught by an automated test — 121.6 must be manually sanity-checked (or `bun run typecheck` plus a careful read-through of the diff) against the existing primary-upstream editor's behavior before being considered done |

## 9. Open questions

1. **VPN-mode records have no failover in this first cut (§3.4).** Should a follow-up plan extend the same idea to `vpn-helper` routes, using `route-checks.ts`'s own `egress` check as the failure signal instead of this plugin's `onFailure` hook? Proposed: only if the owner's fleet actually runs `direct`/backup-chain records in VPN mode in practice — not assumed here.
2. **Should `failureThreshold` have a Studio-exposed minimum/maximum**, or is any positive integer accepted as-is? Proposed: accept any positive integer, no artificial ceiling — the owner runs a large, varied modem fleet and a blanket cap would be guessing at a number nobody asked for.
3. **(New, from 121.6) There is no generic plugin→WS broadcast capability in this codebase** — a tier-C plugin's only wired path to a live client update is `ctx.log` (`plugin.log`) or a poll of its own HTTP routes; there is no `ctx.broadcast()` a plugin can call to push a typed event the way core's own `device.*`/`job.*` messages do. This plan worked around it (the failover chip polls; the event rides `plugin.log`'s `fields` bag) rather than build that capability, which is real, separate, farm-wide infrastructure work benefiting every plugin, not just this one. Proposed: a future plan, scoped only if another plugin ALSO needs live push (a single data point — this plan alone — is thin justification for new core surface).
