# Plan 22.1 — M12a : adb Deadlines and Queue Safety

> Status: implemented — timeout table, coded errors, and profile-based deadlines shipped as designed
> Ships: packages/adb/src/timeouts.ts
> Depends on: Plans 01–16 complete. **Blocks Plans 23–28** (every later plan in the M12 series assumes no adb call can hang).
> Spec references: §10.4 (adb serialisation), §16 (NFR).

---

## 1. Goals

- No adb code path can wait indefinitely. Every read, connect, and handshake carries a deadline.
- A hung command **releases its per-device queue slot** instead of parking it for the lifetime of the process.
- `exec()` cannot be asked to wait forever: there is no API shape that expresses an infinite timeout, and a hard ceiling clamps anything larger.
- Command output is bounded; a runaway command fails with a coded error instead of growing the heap.
- A per-device queue has a maximum depth and rejects beyond it, instead of accepting unbounded work.
- An `AbortSignal` cancels a command whether it is queued or already executing.
- Every failure mode is a distinct coded error a caller can act on.

## 2. Non-goals

- Changing how many commands may run at once — Plan 23 (concurrency scaling).
- Device health, circuit breaking, quarantine on repeated failure — Plan 23.
- Long-running / streaming commands (`logcat`, `top`) — Plan 24. This plan makes short commands safe; it deliberately keeps `exec()` one-shot.
- Any user-facing feature. Nothing in Studio changes.
- Metrics endpoints. This plan adds the counters; Plan 23 exposes them.

## 3. Context and design decisions

### 3.1 The bug this plan closes is already documented in our own code

`packages/scrcpy/src/session.ts:90-98` records what happened the last time a long-lived command went through the adb queue:

> *"routing it through the queue parked a slot forever, so every later shell command on that device queued behind a process that never exits. Volume keys did nothing, the ui-server inspector timed out and fell back, and none of it reported an error: the commands were not failing, they were never running."*

That was worked around by launching scrcpy through the adb CLI instead. The underlying hazard was never fixed: `AdbClient.exec()` still has no timeout of any kind, so any command that does not return leaves a permanently poisoned device.

An audit of `packages/adb/src/` confirms there is not one timeout in the exec path:

| Location | Current behaviour | Failure |
|---|---|---|
| `socket.ts:114` `Bun.connect` | no `connectError`, no timer | a wedged adb server hangs the connect |
| `socket.ts:138,149` `queue.take(n)` | waits for n bytes forever | a device that never sends `OKAY` hangs |
| `socket.ts:158` `takeUntilEnd()` | waits for the peer to close | `logcat` hangs and the buffer grows without bound |
| `socket.ts:162` `close()` | `socket.end()` (FIN) | does not force a peer that ignores it |

### 3.2 Two clocks, not one

A single timeout conflates two different failures. "The device did not answer in 15 s" is a device problem; "this command sat behind 40 other commands for 15 s" is a load problem. Reporting the second as the first would make Plan 23's health checks quarantine perfectly healthy devices under load.

So each call carries two budgets:

- **`queueTimeoutMs`** (default 30 000) — how long the task may wait for its turn. Exceeding it is `E_ADB_BUSY`.
- **`execTimeoutMs`** (default 15 000) — how long execution itself may take, measured from the moment the task starts. Exceeding it is `E_ADB_TIMEOUT`.

### 3.3 A timeout table, not one constant and not string sniffing

Call sites have genuinely different profiles: `getprop` returns in milliseconds, `uiautomator dump` legitimately takes many seconds. One global value is either too tight for the slow ones or useless for the fast ones.

The tempting alternative — inspecting the command string to pick a timeout — is fragile the moment a command is composed (`sh -c '...'`, pipes, `&&`). Instead the **caller names a profile**, and unnamed calls get `default`. The mapping lives in exactly one file.

### 3.4 Why the ceiling matters more than the default

Defaults get overridden; that is fine. What must not exist is a way to express "wait forever", because that is how this class of bug returns. `execTimeoutMs` is clamped to `MAX_EXEC_TIMEOUT_MS` (120 000) and rejects `0`, `Infinity`, and negatives at the type and runtime level. Streaming needs a different shape entirely, and gets one in Plan 24 — a separate method, not a bigger number here.

### 3.5 Terminate, not end

`socket.end()` sends FIN and waits politely. For a timeout that is the wrong verb: the whole point is that the peer is not behaving. Bun exposes `socket.terminate()` (verified in `bun-types@1.3.14`, `bun.d.ts:5852`), which resets the connection. Timeouts and aborts terminate; normal completion ends.

Bun also provides `socket.timeout(seconds)` and a `timeout?(socket)` handler (`bun.d.ts:5840`, `SocketHandler`). That is an **idle** timer — useful in Plan 24 for streams, but not sufficient here: a healthy `dumpsys` can be silent for several seconds and then produce everything at once. This plan uses absolute deadlines; Plan 24 adds idle timers on top for streams.

## 4. Technical design

### 4.1 New file: `packages/adb/src/timeouts.ts`

```ts
/** Nothing may exceed this, whatever a caller asks for. */
export const MAX_EXEC_TIMEOUT_MS = 120_000

export const DEFAULT_QUEUE_TIMEOUT_MS = 30_000
export const DEFAULT_CONNECT_TIMEOUT_MS = 2_000
export const DEFAULT_HANDSHAKE_TIMEOUT_MS = 3_000
export const DEFAULT_MAX_OUTPUT_BYTES = 256 * 1024

/**
 * Per-call-site execution budgets (Plan 22.1 §3.3). Callers name a profile;
 * the string of the command is never inspected to guess one.
 */
export const ADB_TIMEOUTS = {
  /** getprop, wm size, settings get — instant or broken. */
  probe: 5_000,
  /** input tap/keyevent — must not lag behind manual control. */
  input: 5_000,
  /** dumpsys battery — runs periodically, must fail fast. */
  battery: 8_000,
  /** screencap -p — the fallback video path. */
  screencap: 10_000,
  /** am start / am force-stop / pm list. */
  appLifecycle: 15_000,
  /** uiautomator dump — genuinely slow on a loaded device. */
  inspectorDump: 20_000,
  default: 15_000,
} as const

export type AdbTimeoutProfile = keyof typeof ADB_TIMEOUTS

export function resolveExecTimeout(opts?: { timeoutMs?: number; profile?: AdbTimeoutProfile }): number {
  const raw = opts?.timeoutMs ?? ADB_TIMEOUTS[opts?.profile ?? 'default']
  if (!Number.isFinite(raw) || raw <= 0) throw new AdbError('E_ADB_BAD_TIMEOUT', `invalid execTimeoutMs: ${raw}`)
  return Math.min(raw, MAX_EXEC_TIMEOUT_MS)
}
```

### 4.2 Errors — `packages/adb/src/errors.ts`

Add codes (keep `AdbError`'s existing shape):

| Code | Meaning |
|---|---|
| `E_ADB_CONNECT_TIMEOUT` | could not reach the adb server within `connectTimeoutMs` |
| `E_ADB_HANDSHAKE_TIMEOUT` | connected, but no `OKAY` within `handshakeTimeoutMs` |
| `E_ADB_TIMEOUT` | execution exceeded `execTimeoutMs` |
| `E_ADB_BUSY` | queue depth exceeded, or `queueTimeoutMs` elapsed while waiting |
| `E_ADB_OUTPUT_LIMIT` | output exceeded `maxOutputBytes` |
| `E_ADB_ABORTED` | the caller's `AbortSignal` fired |
| `E_ADB_BAD_TIMEOUT` | a caller passed a non-finite or non-positive timeout |

### 4.3 `AdbSocket` — `packages/adb/src/socket.ts`

```ts
export interface AdbSocketOptions {
  connectTimeoutMs?: number
  /** Hard cap on buffered bytes; exceeding it ends the queue with E_ADB_OUTPUT_LIMIT. */
  maxBytes?: number
}

static async connect(host: string, port: number, opts?: AdbSocketOptions): Promise<AdbSocket>
```

Changes:

1. `connect()` races `Bun.connect` against a `connectTimeoutMs` timer and supplies a `connectError` handler, so a refused or black-holed connect rejects with `E_ADB_CONNECT_TIMEOUT` instead of hanging.
2. `ByteQueue` gains:
   - `abort(err: unknown): void` — rejects any waiter and marks the queue dead, so a later `take()` fails immediately rather than waiting on a socket nobody is reading.
   - a `maxBytes` guard in `push()`: once `length > maxBytes`, call `abort(new AdbError('E_ADB_OUTPUT_LIMIT', ...))`.
3. `readStatus()` and `readBlock()` accept `{ timeoutMs }` and race the read against it, throwing `E_ADB_HANDSHAKE_TIMEOUT`.
4. `close(force = false)` → `force ? this.socket.terminate() : this.socket.end()`.
5. `readUntilClose()` keeps its shape but is now only reachable from a caller that has already imposed a deadline (see 4.4). Its doc comment says so explicitly.

`ByteQueue.take()` still throws on a concurrent read; `abort()` must clear `this.waiter` so an aborted socket cannot deadlock a retry on a fresh socket.

### 4.4 `AdbClient.exec` / `execOut` — `packages/adb/src/client.ts`

```ts
export interface AdbExecOptions {
  /** Named profile from ADB_TIMEOUTS; ignored when timeoutMs is given. */
  profile?: AdbTimeoutProfile
  /** Absolute execution budget, clamped to MAX_EXEC_TIMEOUT_MS. */
  timeoutMs?: number
  /** How long the task may wait for its turn in the per-device queue. */
  queueTimeoutMs?: number
  maxOutputBytes?: number
  signal?: AbortSignal
}

exec(serial: string, cmd: string, opts?: AdbExecOptions): Promise<string>
execOut(serial: string, cmd: string, opts?: AdbExecOptions): Promise<Uint8Array>
```

The task body becomes:

```
withDeadline(execTimeoutMs, async (deadlineSignal) => {
  socket = await AdbSocket.connect(host, port, { connectTimeoutMs, maxBytes })
  try {
    socket.send(`host:transport:${serial}`); await socket.readStatus({ timeoutMs: handshake })
    socket.send(`shell:${cmd}`);             await socket.readStatus({ timeoutMs: handshake })
    return await socket.readUntilClose()
  } finally {
    socket.close(/* force */ deadlineSignal.aborted || callerSignal.aborted)
  }
})
```

On deadline or abort: the socket is **terminated**, `ByteQueue.abort()` unblocks the pending read, the task rejects, and `PerDeviceQueue`'s existing `finally` releases the semaphore slot. That last point is what actually fixes the parked-slot bug — the release already exists, it was simply never reached.

### 4.5 `PerDeviceQueue` — `packages/adb/src/queue.ts`

```ts
export interface QueueRunOptions {
  queueTimeoutMs?: number
  signal?: AbortSignal
  /** Rejects with E_ADB_BUSY when the chain for this serial is already this deep. */
  maxDepth?: number
}

run<T>(serial: string, task: () => Promise<T>, opts?: QueueRunOptions): Promise<T>
```

Rules:

1. **Depth cap** (default 32, configurable): if `pending(serial) >= maxDepth`, reject with `E_ADB_BUSY` *before* enqueueing. Nothing is accepted that we do not intend to run.
2. **Queue timeout**: a timer starts at enqueue. If the task has not started when it fires, remove it from the chain and reject `E_ADB_BUSY`. The timer is cleared the instant the task starts — waiting is bounded, execution is not bounded by this clock.
3. **Abort while queued**: if `signal` fires before the task starts, drop it without ever opening a socket.
4. The `pending` bookkeeping must stay correct on all three paths, or the depth cap slowly poisons a device. This is the single most test-worthy part of the change.

**22.2 — `AdbSocket` deadlines**
- Add `AdbSocketOptions`, the connect race, and `connectError` per §4.3.
- Add `ByteQueue.abort()` and the `maxBytes` guard.
- Add `{ timeoutMs }` to `readStatus`/`readBlock`.
- Change `close(force?)` to pick `terminate()` vs `end()`.

**22.3 — `PerDeviceQueue` safety**
- Add `QueueRunOptions`, the depth cap, the queue timer, and abort-while-queued (§4.5).
- Keep `pause`/`resume`/`waitIdle` semantics unchanged — the Toolchain Manager's adb swap depends on them.
- Result: `queue.test.ts` covers depth rejection, queue timeout, abort while queued, and `pending()` returning to 0 on every path.

**22.4 — `AdbClient.exec` / `execOut`**
- Add `AdbExecOptions`; thread `queueTimeoutMs`/`signal`/`maxDepth` into `queue.run` and the deadline into the task body (§4.4).
- Force-terminate the socket when the deadline or the caller's signal fired.
- Result: a hung command rejects `E_ADB_TIMEOUT` and the next command on the same serial runs normally.

**22.5 — Name a profile at every call site**
- Work through the table in §4.6. Add the options passthrough to `AdbTransport`.
- Result: `grep -rn "\.exec(" packages --include='*.ts' | grep -v node_modules` shows no adb exec without a profile or explicit timeout.

**22.6 — Counters (consumed in Plan 23)**
- `AdbClient` accepts `onMetric?: (m: { serial: string; profile: string; ms: number; outcome: 'ok'|'timeout'|'busy'|'error' }) => void` and calls it once per task.
- No endpoint, no storage. Plan 23 wires it up.

## 6. Acceptance criteria

1. No adb read, connect, or handshake can block forever; every path has a deadline with a coded error.
2. `AdbClient.exec` rejects `E_ADB_BAD_TIMEOUT` for `0`, negative, `NaN`, and `Infinity`, and clamps anything above `MAX_EXEC_TIMEOUT_MS`.
3. A command against an unresponsive endpoint rejects within its budget, and the **next** command on the same serial succeeds — the slot was released.
4. Output beyond `maxOutputBytes` rejects `E_ADB_OUTPUT_LIMIT` and does not grow the heap further.
5. Enqueueing beyond `maxDepth` rejects `E_ADB_BUSY` without opening a socket.
6. An `AbortSignal` fired while queued prevents execution; fired mid-flight it terminates the socket and rejects `E_ADB_ABORTED`.
7. `pending(serial)` returns to 0 after every combination of success, timeout, abort, and depth rejection.
8. Existing behaviour is unchanged with a real device: stream start, manual control, and a script job all still work (smoke test in §7).
9. `bun run typecheck` passes; `bun test` is green.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A profile is set too tight and healthy commands start failing (`uiautomator dump` on a loaded device). | Profiles are generous by default; every timeout is logged at `warn` with the profile name so tuning is evidence-based, and Plan 23 makes them user-settable. |
| `terminate()` on a socket the adb server is mid-write on leaves the server in a bad state. | Terminate only on the timeout/abort path, never on normal completion. The adb server tolerates client resets; this is what its own CLI does on Ctrl-C. |
| Queue bookkeeping regresses and `pending` drifts, so the depth cap slowly bricks a device. | A dedicated test asserts `pending()` returns to 0 on all four exit paths; `pending()` is also exported for the Plan 23 metrics endpoint. |
| The screencap fallback path becomes flakier because 10 s is too tight on a slow device. | The profile is per call site; if the smoke test shows otherwise, raise `screencap` alone rather than the default. |

## 9. Open questions

1. Should `queueTimeoutMs` be per profile as well? Currently one default (30 s) for everything. Deferred until Plan 23's metrics show whether queue waits actually approach it.
2. When a shell command times out, the process on the device usually receives SIGHUP and dies — but not always. Plan 24 needs an explicit kill path for streams; whether one-shot commands need the same sweep is left to that plan's findings.
