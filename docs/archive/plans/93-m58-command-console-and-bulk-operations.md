## 1. Goals

- **One command, N devices, N answers — with the answers legible.** An
  operator types one command, picks one device or the whole farm, and gets a
  report that makes the *odd one out* the thing they see first, not something
  they scroll for.
- **Nothing is ever silently skipped.** Every device in the target that did not
  run the command appears in the report with the reason, in the words the lease
  manager already uses. This applies to fan-out and to every bulk operation.
- **History is durable, per-user, browsable, and re-runnable** — the same
  record whether the command went to one device or a hundred, so there is one
  history, not two.
- **Saved commands are a farm asset, not a personal bookmark**: named,
  described, visible to the team, owned by whoever made them, and usable as the
  target of a schedule later.
- **Fan-out is authorised exactly as strictly as the terminal it extends** —
  the same role gate, the same farm switch, the same lease rule, plus its own
  opt-in — and is *never* reachable through a path that only checks `job.run`.
- **A fan-out in flight is stoppable**, and stopping it means pending members
  never start, not "wait for 100 commands to finish".
- **A destructive fan-out is hard to do by accident and easy to do
  deliberately** — a staged first-N run, a target preview naming every device,
  and a typed confirmation above a threshold. None of it is described as
  security.
- **Bulk push, bulk pull and bulk install are one mechanism with one report**,
  built on the batch machinery that already runs bulk install, with the files a
  bulk pull collected reachable as one download.
- **The farm's existing budgets are respected, not duplicated**: the exec
  semaphore already autoscales (F23), the transport already has a buffer
  budget (F21), and this plan sizes itself against both rather than inventing a
  third.
- **The permission hole in the batch path is closed** as part of the same work,
  because bulk push and bulk pull would otherwise widen it from "install an APK"
  to "read and write any file on any device".

## 2. Non-goals

- **Not a live-tailing fan-out.** `monitor.*` streams stay one-device. Twenty
  concurrent `logcat` streams into one browser tab is the failure mode this
  plan exists to avoid, and the Monitor tab already does one device well,
  including save-as-artifact.
- **Not a pty, and not interactive stdin.** Plan 26 §9 already records that;
  fan-out makes it less appropriate, not more.
- **Not a command allowlist or denylist as a security control.** Plan 26 §3.4
  settled this and it is still right: `sh -c`, a backtick, or an alias defeats
  any parser. §3.14 says exactly what the guards here are and are not.
- **Not a change to the trust model.** Spec §11.3 stands: an authenticated,
  leased operator is a trusted operator. This plan makes fan-out obey that
  model; it does not widen or narrow it. (It does correct one place where the
  code is already wider than §11.3 claims — F10.)
- **Not co-control.** Running a command on a device another operator or a job
  is driving is refused, with that holder named. **Plan 91** owns co-control,
  and its design deliberately does **not** extend to `shell.exec` — §3.8 states
  the assumption precisely and why this plan does not build for a widening that
  91 has explicitly refused.
- **Not the focused control window, its button panel, Wall-view selection, or
  multi-device input mirroring.** All four are **plan 91**. §3.16 states how
  this plan's toolbar actions attach to whatever selection exists, and adds no
  selection mechanism of its own.
- **Not scheduling, repetition, or jitter.** **Plan 94** owns "N devices,
  `count` times, on a jittered clock", and declares the seam itself: an optional
  `pacing` block on `POST /api/batches`, absent meaning today's behaviour. This
  plan's bulk operations are batches, so they inherit it with no work; §3.10
  states the rest.
- **Not per-member parameters.** A different file pushed to each device (plan
  94 §9 Q3 names it `batch_member_params`) is a real, separable feature that
  neither plan builds. Bulk push here is one artifact to N devices, and says so.
- **Not the guest agent.** **Plan 90** owns that; nothing here needs an
  on-device helper — every command goes through the existing `ShellPort`, so
  local and node-owned devices work with no branch.
- **Not a farm-wide job-concurrency setting.** F23 shows none exists; adding
  one is a scheduler change with its own reasoning and belongs in its own plan.
- **Not artifact storage for command output.** §3.6 caps and truncates instead,
  and says why.

## 3. Context and design decisions

### 3.1 The console is one feature; bulk operations are another; they are not the same shape

It is tempting to build one mechanism for "do a thing to N devices" and route
everything through it. That would be wrong here, and the reason is visible in
the code rather than aesthetic.

A **batch member is a job** (F9). A job takes a job lease, flips the device to
`busy`, is claimed by a scheduler tick, and is refused outright on a device
someone is currently controlling. That is exactly right for a 90-second APK
install and exactly wrong for a 200-millisecond `getprop`:

1. **Latency.** Dispatch → transaction → `scheduler.kick()` → claim SQL →
   executor host → lease → run. An operator asking twenty phones what build
   they are on expects an answer in about a second, and a queue round-trip per
   device is not that.
2. **Lease semantics are inverted.** A job cannot claim a device in `manual`
   status. The one device you are *looking at* — the one you already hold — is
   the one a batch would refuse (F19, `device_held_by_other` / the claim SQL's
   `d.status = 'idle'`). For a fleet query that is backwards.
3. **The authorisation gate is wrong, and demonstrably so.** `POST /api/batches`
   checks `job.run` and nothing else (F10). Registering an `internal:shell`
   executor would hand a farm-wide shell to every holder of an operator-set
   permission, bypassing `device.shell`, `shell.mode` and the lease — the
   precise widening spec §11.3 exists to bound. This is not hypothetical: the
   same hole is already open for `internal:install` today.

So: **the console owns shell commands at every target size (N = 1 to N = all),
and batches own file and APK operations at every target size.** Neither is
split by target size, which is what would have made this a half-feature. They
are split by what the operation *is*, and each keeps the gate that belongs to
it. The parts that must not diverge — the report shape, the skipped-with-reason
discipline, the retry actions — are shared components, not shared plumbing
(§3.15).

### 3.2 What is deliberately reused, verbatim

The single largest risk in a plan like this is re-implementing something that
already works. Reused without modification:

| Reused | From | Why not re-derive |
|---|---|---|
| `ShellExecResult` and the whole result rendering — stdout, stderr as its own stream, the coloured exit badge, duration, truncation | F2 | It is correct. The fan-out row *is* this row with a device label on it. |
| `checkInputAllowed` and its five refusal codes | F18 | It is the one input/shell/transfer policy in the codebase. A second one would eventually disagree with it. |
| `canUseShell(role, shell.mode)` | F18 | Same. |
| `ShellPort.exec` (local and remote, one interface) | F2 | Cloud parity for free; no branch in the runner. |
| `resolveTarget` / `resolveCluster` for *membership* | F30 | The console and batches must agree on what "this cluster" means. |
| The exec semaphore and per-device queue | F23 | A fan-out is N ordinary execs. It needs no new concurrency mechanism at all — see §3.5. |
| `saveForDevice` / the artifact store | F12 | Only for bulk pull, which genuinely produces files. Console output does not (§3.6). |
| `createBatch`, `computeBatchStatus`, `cancelQueuedInBatch`, `rerun-failed`, the batch detail page | F9 | Bulk push/pull are `internal:*` executors beside `internal:install`, and inherit all of it. |
| `redactShellCommand` | F5 | The stored command text gets the same log-hygiene pass the event stream already applies. |

### 3.3 The persistence question, answered before a table is added

Three candidate stores exist. Each was checked against what history and saved
commands actually need.

**`farm_settings`** — one JSON row, `id = 1`, whole-object `safeParse` on every
write, shallow per-section merge (F7). A list of saved commands *could* live
here, and it would be wrong: `SchemaForm` renders forms, not CRUD lists, so it
would have no usable UI; every save rewrites the entire settings blob, so two
admins editing different sections lose each other's work; and there is no
ordering, no ownership, and no per-row timestamp. History is worse still — it
is append-heavy and per-user, and `farm_settings` is neither.

**`kv_entries`** — namespaced, scoped, CAS-versioned, TTL'd, with a real store
API (F7). It is genuinely good, and it is genuinely not this: its scope axis is
`global | device` with no user dimension, its namespace axis is *the owning
plugin or script* (injected by the runtime, never chosen by a caller), it has
no ordering, and `list()` paginates by key. A saved-command list here would be
N rows keyed by UUID holding JSON blobs — a table implemented badly inside a
table, with every index and every foreign key thrown away. Its permission is
also wrong: `kv.manage` is admin-only and deliberately outside the `OPERATOR`
set, so operators could not manage their own saved commands.

**`device_events`** — the closest near-miss, and the most instructive. It
already records every command with its actor, cwd, exit code, byte count and
duration (F5). But `eventInputDays` defaults to **3**, the text is redacted,
there is no user axis, and there is no cross-device query. It is an *audit
stream*, and turning it into history would mean raising a high-volume stream's
retention tenfold for the sake of a low-volume feature — the wrong trade at
exactly the wrong table.

**Decision: one new pair of tables, `command_runs` and `command_run_members`,
plus one for `saved_commands`.** And a specific consequence follows:

> **A single-device terminal command is a run with one member.** `shell.exec`
> writes the same record. There is one history, not "terminal history" and
> "console history", and re-running something from history does not care where
> it originally came from.

That collapses two concepts into one and is the reason this is two tables and
not four. History is not a table — it is `GET /api/command-runs?mine=1`.

`device_events` keeps doing its job unchanged: it remains the 3-day audit
stream, and the console writes to it exactly as `shell.exec` does today. The
two records answer different questions with different retentions and different
readers, and that is stated in the schema comment so nobody later "de-duplicates"
them.

### 3.4 What a fan-out run actually is

```
run   := { cmd, target, stages, concurrency, createdBy, startedAt, status }
member:= { runId, deviceId, seq, status, exitCode, durationMs, output, outputHash, truncated, skipReason }
```

Member statuses: `pending → running → ok | failed | skipped | cancelled`.

- **`ok`** — the command ran and exited 0.
- **`failed`** — the command ran and exited non-zero, *or* could not be run for
  a device-side reason (adb error, deadline). The distinction is in
  `exitCode` (a number vs `null`) plus `error`, exactly as the terminal already
  distinguishes them (F2, F22).
- **`skipped`** — the device was in the target but was never sent the command,
  with `skipReason` carrying `checkInputAllowed`'s own code and message
  verbatim. **This is a first-class outcome, not an absence.**
- **`cancelled`** — the run was cancelled before this member started.

Run statuses: `running | awaiting-continue | ok | failed | cancelled`, derived
from the members the same way `computeBatchStatus` derives a batch's (F9) — one
function, recomputed, never incremented.

### 3.5 Concurrency: there is nothing to build

A fan-out is N ordinary `ShellPort.exec` calls. Each one goes through the
per-device queue and the farm-wide exec semaphore, which already autoscales
`min(24, max(6, ceil(n * 0.75)))` (F23). A 100-device fan-out therefore drains
at whatever rate the adb subsystem can actually sustain, with no new budget,
no new setting, and no risk of the two disagreeing.

What the runner adds is not a limit but **legibility**: it dispatches members
through a small worker pool of `shell.fanoutConcurrency` (default `0` = "as
many as the semaphore will take", capped internally at 32 in-flight promises so
the core is not holding 100 pending awaits for a 100-device run), and it emits a
`command.progress` frame at most every 250 ms carrying the deltas since the last
one.

That last number matters. One message per member transition means 200 messages
for a 100-device run; one coalesced frame per 250 ms means roughly four per
second regardless of fleet size. The operator sees a bar that moves and counts
that climb, and the socket carries a bounded, predictable trickle (F21, H2).

**What the operator sees while a 100-device run drains:** the target preview is
rendered *before* anything starts, so all 100 rows exist immediately as
`pending`; they flip to `running` and then to an outcome as the semaphore lets
them through. There is never a blank screen and never an unexplained wait.

### 3.6 Output: bounded on the wire, bounded at rest, and no artifacts

The scenario that kills a naive design: 20 devices, one command that emits 5 MB
of logcat each. Three separate caps, each with a number chosen against a number
that already exists:

1. **On the device side**, a fan-out member runs with
   `shell.fanoutMaxOutputBytes` (default **32 KB**), not the terminal's 256 KB
   (F22). Above it, the result is `truncated: true`, exactly as the terminal
   already reports. Worst case at rest: 100 × 32 KB = 3.2 MB per run.
2. **On the wire**, a member delta carries **no output at all** — only
   `{ deviceId, status, exitCode, durationMs, outputHash, truncated }`. The
   body travels once per *distinct* output as a `command.output` frame capped
   at `shell.fanoutPreviewBytes` (default **2 KB**). Worst case, a fully
   heterogeneous 100-device farm: 100 × 2 KB ≈ 200 KB, deliberately **under**
   the 512 KB `MAX_BUFFERED` budget (F21, H2). On a homogeneous farm (H1) it is
   two or three frames.
3. **Full output** (up to the 32 KB retained) is fetched **over HTTP, per
   device, on demand** — `GET /api/command-runs/:id/members/:deviceId/output`.
   It never touches the WebSocket, so no amount of clicking around in the
   report can congest the control plane.

**No artifacts are created for command output, and that is deliberate.** A
fan-out is a *survey*; if you need 5 MB off a phone, that is the Monitor tab
(which already has save-as-artifact) or a script. Storing per-device blobs would
add an artifact-lifecycle problem — dedup, ownership (`artifacts` requires a
`jobId` or `deviceId`, and a run is neither, F12/F14), and GC — in exchange for
a capability the product already provides better elsewhere. When output is
truncated the row says so and offers **"open in Monitor"** and **"open this
device's terminal"**, which is where that need actually belongs.

The output hash is `Bun.hash` (wyhash, 64-bit) over `exitCode + "\0" + stdout +
"\0" + stderr` — over the *retained* bytes, not the preview, so two devices
whose first 2 KB match but whose tails differ never group. It is a grouping key,
not a security primitive, so a cryptographic hash would buy nothing and cost a
sha256 pass over up to 3.2 MB per run.

### 3.7 Cancellation, staging, and surviving a restart

- **Cancel** flips every `pending` member to `cancelled` synchronously — they
  never start — and aborts in-flight members through the `AbortSignal` the adb
  layer already honours (plan 22.1). A command already executing *on the phone*
  may still complete; the report says `cancelled` and the row carries "the
  command may have completed on the device". Claiming otherwise would be a lie,
  and the terminal's own honesty about emulated cwd is the precedent (plan 26
  §3.7).
- **Staged rollout.** The run form offers "run on the first N first"
  (`stage.firstN`, default off, one click to enable). After stage 1 the run
  enters `awaiting-continue` and shows **Continue** / **Stop** beside the stage
  1 results. No lease is held while waiting (§3.8), so nothing is blocked. A run
  left waiting past `shell.fanoutStageWaitSec` (default **900**) is cancelled
  with `stage_timeout`. This is the guard that actually saves an operator from a
  bad `pm uninstall`: run it on one phone, read the exit code, then continue.
- **Core restart.** Members left `pending` or `running` are swept at boot to
  `cancelled` with `error: 'the core restarted'`, and the run to `cancelled` —
  the exact shape of `failOrphanRunning` (F29). A console run is deliberately
  **not** resumable: it is an interactive act by a person who is no longer
  attached, and silently continuing to fire commands at a farm after a restart
  is the opposite of what anyone wants. Work that must survive a restart is
  work that belongs in a batch or (plan 94) a schedule, and the plan says so.

### 3.8 Authorisation: the obvious question, answered

`shell.exec` requires role + `shell.mode` + **the manual lease on that device**
(F18). Fan-out to twenty devices cannot require twenty leases the operator
acquired by hand, and must not require none.

**Decision — one gate evaluated once, one gate evaluated per member.**

*Once per run*, before anything starts:
- `canUseShell(role, shell.mode)` — unchanged, the identical call the terminal
  makes (F18).
- `shell.fanoutEnabled` — a **new, separate opt-in**, on the exact precedent of
  `shell.endpointEnabled` (F25): running one gated shell and running a hundred
  at once are different decisions, and the second should never be a discovery.
  Its default follows `shell.mode`'s asymmetry rather than the endpoint's flat
  `false`: **`true` on a loopback (single-user) install, forced to `false` in
  server mode at config load**, where the auth mode is derived from the bind
  address and the Zod schema cannot see it. A laptop farm gets the feature; an
  exposed farm gets a decision.
- `shell.fanoutMaxDevices` (default `0` = unlimited) — a farm may cap the blast
  radius outright.
- `canUseDevice` per resolved target — device ownership, the same check
  `createBatch` already makes (`dispatch.ts:153-157`). A device owned by someone
  else is refused before the run starts, not skipped mid-flight.

*Per member*, immediately before its exec:

```
admitMember(deviceId, clientId):
  a = leases.checkInputAllowed(deviceId, clientId)
  if a.ok                       -> run, hold nothing (the operator already holds it)
  if a.code == 'no_lease'       -> acquireManual(deviceId, clientId, userId)   // idle: succeeds outright (F19)
                                   run; releaseManual(...) in a finally
  otherwise                     -> skipped, skipReason = { code: a.code, message: a.message }
```

The consequences, stated plainly because they are the point:

- **A device you already control runs the command immediately.** No lease churn,
  no state change. This is what a batch could never do (§3.1).
- **An idle device is briefly, genuinely held by you** while your command runs —
  typically well under a second — and released. That is not a workaround; it is
  correct. While your command runs on a phone, nobody else should be driving it.
- **A device someone else is controlling is skipped and says so, naming them.**
  `not_lease_holder`'s message is already "another client is controlling this
  device", and `heldBy` (plan 71) supplies the name for the report.
- **A device running a job is skipped** with `device_busy` — "Device is running
  an automation job". Never taken over: `acquireManual` refuses a job hold
  unconditionally (F19), and this plan does not argue with that.
- **Offline / quarantined** are skipped with `device_unavailable`.

**The interface to plan 91, which is narrower than it first looks.** Plan 91
(co-control / *Assist*) is designing a second authorisation object beside the
lease — and it is explicit that `checkInputAllowed` is **not modified**, that
the grant covers **exactly five verbs** (`input.tap`, `input.swipe`,
`input.gesture`, `input.key`, `input.text`), and that "`shell.exec`, `inspect.*`,
`clipboard.set`, the adb endpoint, and install/push/pull are reachable only by
the lease holder, exactly as today, and a test proves it"
(`docs/plans/91-m56-co-control-and-mirror-input.md` §1, §3.1, §3.2).

So this plan assumes **the opposite of the convenient thing**: co-control will
*not* make a fan-out shell command reach a device someone else holds, and
"skipped, naming the holder" is the **permanent** answer, not a placeholder.
That is the right answer on plan 91's own reasoning — the same function that
authorises a tap authorises a root-equivalent shell command, and spec §11.3's
trust decision is about *the lease holder*, not about whoever confirmed a
dialog. Widening it for fan-out would re-open exactly the door plan 91 closed.

The one concrete consequence for this plan: `admitMember` is a single function,
so if the owner ever decides a fan-out *should* reach assisted devices (§9 Q6),
there is one call site to change and one test to update — but nothing here is
built in anticipation of that, and no surface degrades if it never happens.

Hold is **per member, not per run** (H4): acquire immediately before the exec,
release immediately after. A 100-device run therefore never holds 100 devices at
once — it holds at most `concurrency` of them, for the duration of one command
each. For a staged run, devices are re-admitted at each stage; a device that
became held between stages is reported as skipped for that stage, which is
correct rather than a defect.

The cost is `lease.changed` traffic — up to two broadcasts per member (F20's
map is in-memory, so the write itself is free). To keep that legible rather than
alarming, `Lease` gains `purpose: 'control' | 'command'`, so Studio's holder
badge renders "running a command" instead of "alice took control" for a
sub-second hold. If the ladder in §7.3 shows the broadcast rate itself biting,
the designed-but-not-executed mitigation is coalescing (§8).

### 3.9 History

History is `GET /api/command-runs`, keyset-paginated on `(startedAt DESC, id
DESC)` through the existing `api/pagination.ts` helper, with:

- `?mine=1` — the default in Studio. Your commands.
- **Everyone's history is visible to admins**, and to operators only for
  devices they can use (`canUseDevice`), matching how `device_events` already
  behaves — a farm is a team tool (plan 26 §3.8: "seeing that a colleague just
  ran `pm clear` explains the device's behaviour far better than discovering it
  later in an audit log").
- `?deviceId=`, `?q=` (substring over `cmd`), `?status=`.

Bounded by two budgets, both farm settings: `shell.commandRunRetentionDays`
(default **14**, swept by the existing retention GC alongside events and
artifacts) and `shell.commandRunsPerUser` (default **500**, trimmed
oldest-first on insert). At the caps, worst case per user is 500 runs; a
single-device run holds one member row of at most 32 KB, so the ordinary
interactive case is a few megabytes and a fan-out-heavy user is bounded by
retention.

The stored `cmd` is passed through `redactShellCommand` (F5) — the same
log-hygiene pass, not a security control, and the same caveat applies.

Arrow-up in the terminal keeps working exactly as it does today (F3) and is
seeded from the last 50 entries of your own history on mount, so the recall an
operator already has stops being wiped by a remount. The **History** panel is
the browsable form: command, when, target, and an outcome chip, with **Run
again** (same target) and **Run again on…** (pick a new target).

### 3.10 Saved commands

**Farm-scoped with an owner, not per-user.** A farm is operated by a team, and
a saved command that only its author can see means everyone rewrites the same
`dumpsys battery | grep level`. This matches how scripts and clusters already
work. Visible to all; editable and deletable by the owner or an admin.

```
saved_commands: id, name, description, cmd, defaultTarget (json | null),
                createdBy, createdAt, updatedAt, sortOrder
```

- `name` is unique per farm (a unique index), because "which `battery` do you
  mean" is a question nobody should have to ask.
- `defaultTarget` is a cluster id, a tag set, or null — a saved command that is
  *always* for the `pool:smoke` cluster says so, and the run form prefills it.
  Never enforced: the operator can always retarget.
- **No `dangerous` column.** Whether a command is high-consequence is derived
  from its text by the shared guard (§3.14), evaluated fresh at render and at
  run. A stored boolean would go stale the moment someone edits the command,
  and a stale danger flag is worse than none.
- Capped at `shell.savedCommandLimit` (default **200**) per farm; there is no
  folder tree, because a farm with more than 200 saved commands has a scripts
  problem, not a folders problem.
- Permission: reading needs `device.view`; creating and editing need
  `canUseShell(role, shell.mode)` — you may not save a command you could not
  run.

**Interface to plan 94 (the action recorder and jittered scheduling).** Plan 94
declares the seam from its side and this plan honours it verbatim: *"plan 93
owns 'do this to N devices now'; plan 94 owns 'do this to N devices, `count`
times, on a jittered clock'. The seam is `POST /api/batches` with a `pacing`
block — absent means today's behaviour exactly"*
(`docs/plans/94-m59-action-recorder-and-task-scheduling.md` §3.10, §4.9). So:

- **Bulk push / pull / install need no work at all** to gain pacing. They are
  batches; when plan 94 adds an optional `pacing` block to `POST /api/batches`,
  they inherit it, and this plan's dialogs simply do not send one.
- **A console run is deliberately outside that seam.** A fan-out shell command
  is an interactive act that is not resumable across a restart (§3.7); repeating
  one on a clock is scheduling, and it belongs on the batch/schedule side, not
  in the console.
- **What this plan offers plan 94, without presuming it:** `saved_commands.id`
  is a stable handle and `defaultTarget` is a reusable target expression, so a
  future schedule that wants to repeat a *shell* command has something to key
  on — resolving the text at fire time, exactly as plan 62 has a schedule store
  a *reference* and a job store the *resolution*. Deletion is a real delete, so
  such a reference can dangle and whoever builds it owns that case.

### 3.11 Bulk operations are batches, and here is the argument

Everything a bulk operation needs already exists in the batch machinery (F9),
and bulk install already proves it end to end (`internal:install`, F10's first
half). Rebuilding it would produce a second scheduler, a second concurrency
model, a second cancel path and a second report. So:

- **Bulk install** — ships. Changes: the permission gate (§3.12), skipped
  devices become visible (§3.12), the dialog gains `concurrency`/`order` (F17)
  and an artifact picker (§3.13), and it stops navigating away before a result
  exists (F15).
- **Bulk push** — a new `internal:push` executor beside `internal:install`,
  params `{ artifactId, remotePath }`. Roughly twenty lines: `validateParams`
  through a Zod schema, `run` through `runTransfer`. Everything else —
  concurrency, order, per-device rows, cancel, rerun-failed — is inherited.
- **Bulk pull** — a new `internal:pull` executor, params `{ remotePath }`.
  Same shape. Its output needs one repair and one addition, below.

Both new executors go through `runTransfer` (F26's construction-injection
pattern, since `ExecutorContext` has no transfer or artifact affordance) and
therefore inherit progress broadcasts, cancel-on-signal, and the readiness hold
for free.

### 3.12 The batch permission gate — a defect this plan must not repeat

F10 is a live escalation: `POST /api/batches` with `scriptId: 'internal:install'`
installs an arbitrary APK on every device in a cluster with only `job.run` — no
`device.files`, no lease, and `transfer.enabled: false` does not stop it.
`POST /api/jobs` checks no permission at all. Spec §11.3 states that
install/push/pull are lease-scoped; on this path they are not.

Adding `internal:push` and `internal:pull` without fixing it would widen that
from "install an APK" to **"read or write any file on any device"**, which is
not a trade this plan is willing to make silently.

**Decision.** `JobExecutor` gains two optional declarations:

```ts
export interface JobExecutor {
  validateParams(params: unknown): unknown
  run(job: JobRow, ctx: ExecutorContext): Promise<unknown>
  /** Checked by every dispatch path before a job row exists. Undefined = no extra gate (a script). */
  requires?: {
    /** Evaluated with the farm's `shell.mode`, exactly as the HTTP sibling does. */
    gate?: 'files' | 'shell'
    /** A farm switch that must be on. */
    setting?: 'transfer.enabled'
  }
}
```

`internal:install`, `internal:push` and `internal:pull` declare
`{ gate: 'files', setting: 'transfer.enabled' }`. `validateScriptForRun` — the
one function every dispatch path already funnels through
(`jobs/validate-script.ts:11`, called from `api/batches.ts:162`, `:212`,
`services/job-service.ts:85`, and the schedule runner) — gains the actor's role
and enforces it. One place, four callers, no new door.

The **lease** question is answered differently and honestly: a batch member
holds a *job* lease for the duration of its transfer (F20), which is a real
exclusive hold, just not the operator's manual one. That is correct behaviour —
a batch install must not require the operator to hold twenty manual leases — but
it is **not what spec §11.3 currently says**. §5's documentation step amends
§11.3 to state both paths precisely, per the Definition of Done's rule that a
plan touching a security surface updates the spec in the same commit.

Separately, and in the same step: **`BatchInfo` gains `skipped`** (F11). The
data is already computed at dispatch and thrown away into an audit blob; it gets
a `skipped` JSON column on `batches` and a field on the wire, so every bulk
surface can finally say "17 of 20 — three were offline" instead of "17".
`POST /api/batches/:id/rerun` grows an `only=failed|skipped` parameter beside the
existing `rerun-failed`.

### 3.13 Bulk pull, and the N-files-one-name problem

The naive design writes N files into one directory and loses all but the last.
That failure is already avoided: each pull lands as its own device-scoped
artifact under `artifacts/device-<deviceId>/` with an epoch-millisecond prefix
(F12). Nothing collides on disk today.

What is missing is everything *after* the bytes land:

1. **Provenance.** `registerDeviceArtifact` writes `jobId: null` (F12), so a
   pulled file cannot be traced to the operation that pulled it. Fixed: it takes
   an optional `jobId`, and `internal:pull` passes `job.id`. `artifacts` already
   indexes `(jobId, createdAt)`.
2. **Collection.** `GET /api/batches/:id/artifacts` joins `artifacts.jobId →
   jobs.batchId` and returns one row per device: device label, stableId,
   original filename, size, and a content URL.
3. **One download.** `GET /api/batches/:id/artifacts.zip` streams a **stored
   (method 0, uncompressed) zip** with entry paths
   `<device-label-slug>-<stableId-short>/<original-label>`. Device label first
   because that is how an operator thinks; stableId appended because two phones
   are often both labelled "Pixel 6". No compression: pulled files are usually
   already-compressed media, so deflate would cost CPU across the whole fleet's
   output for nothing, and a stored zip streams with no buffering. Bounded by
   `transfer.maxArchiveBytes` (default **2 GiB**), refused above with
   `E_TRANSFER_TOO_LARGE` — which also keeps it under the 4 GiB boundary where
   zip64 would be required, so the writer stays simple.
   - **Why zip and not tar**, given tar is simpler: a zip opens by
     double-click on Windows and macOS with no tooling. The whole point of the
     archive is that the operator does not have to think.
   - **Why write one at all**: forty files behind forty clicks is the
     half-feature this plan is meant to avoid.
4. **Same-name grouping in the UI.** Twenty devices returning `screenshot.png`
   render as one grouped row with a count chip and a per-device expansion —
   the same instinct as §3.6's output grouping, and the same component.

### 3.14 The dangerous-command guard: what it is, and what it is not

Plan 26 §3.4 rejected command parsing as a security control and was right. This
plan does not reopen that. It extends the existing usability guard and adds
three guards that are about *blast radius* rather than about command text —
which is the thing that actually changed when fan-out arrived.

**Extend, do not invent.** `isHighConsequence` and `HIGH_CONSEQUENCE_PATTERNS`
move out of `TerminalPane.tsx` into `@enkaku/protocol` so Studio and the core
evaluate the identical list, and the existing test file moves with them
unchanged. Additions, each justified against the test file's own warning that
false positives are the greater danger (F24):

| Added | Why | Must still NOT fire on |
|---|---|---|
| `pm uninstall` / `cmd package uninstall` | Irreversible; takes the app's data with it. | `pm list packages`, `pm path`, `pm dump` |
| `pm clear` | Wipes an app's data with no confirmation on-device. | `pm clear-...` does not exist; anchored to the word |

Deliberately **not** added: `am force-stop` (everyday, and the existing test
asserts it must not fire), `settings put` in general (only `global adb_enabled`
is device-wide), `am start` (opening a page is not a device-wide act). Every
addition ships with tests in *both* directions, following the existing file's
structure.

**The three guards that are actually about fan-out:**

1. **A target preview, always.** Before a run starts, the dialog names every
   device that will receive the command *and* every device that will not, with
   the reason. No count without names (H3). This is the guard that stops the
   mistake most often, because most fleet mistakes are targeting mistakes.
2. **Typed confirmation above a threshold.** Above
   `shell.fanoutConfirmThreshold` devices (default **5**), the operator types
   the device count to proceed. Cheap, standard, and it defeats muscle memory
   rather than testing knowledge.
3. **Staged first-N** (§3.7). The only guard here that can actually prevent the
   damage rather than slow it down.

**The server-side acknowledgement, described honestly.** When the shared guard
matches *and* the target is more than one device, `POST /api/command-runs`
requires `acknowledge: { highConsequence: true }` in the body and refuses
without it (`E_ACK_REQUIRED`, naming the pattern that matched). This is **not a
security control** — any client can send the field, and the plan says so in the
code comment beside it, exactly as `TerminalPane.tsx:64-75` already does. What
it buys is different and real: the acknowledgement is **recorded in the audit
row and on the run**, so "twenty phones were rebooted and somebody meant it" is
a fact on the record rather than a reconstruction. A scripted client that sends
it has asserted intent; that is the entire claim.

### 3.15 The report: how N results are shown without drowning anyone

The default view is **grouped by outcome, then by identical output**, sorted so
the exceptions are at the top:

```
┌───────────────────────────────────────────────────────────────┐
│ getprop ro.build.version.release        ▓▓▓▓▓▓▓▓▓░  94 / 100  │
│ 91 ok · 2 non-zero · 4 held · 3 offline        [Stop]  [Rerun]│
└───────────────────────────────────────────────────────────────┘

  ▸ exit 1 · 2 devices                          rack-a-07, rack-c-02
    <stderr preview>
  ▸ skipped · 4 devices — another client is controlling this device
    rack-b-01 (bea), rack-b-03 (bea), …
  ▸ skipped · 3 devices — the device is unavailable (status offline)
  ▾ exit 0 · 91 devices                                    "13"
    rack-a-01 · 210 ms      rack-a-02 · 198 ms      …
```

The decisions behind that sketch:

- **Failures and skips sort above successes, always.** design.md's own rule:
  "one red dot among a dozen devices has to catch the eye immediately".
  Alphabetical-by-device would bury the two rows that matter under ninety-one
  that do not.
- **Identical outputs collapse into one row** (H1). This is the single most
  important decision in the report: on a homogeneous farm it turns 100 rows into
  three, and the two-device outlier becomes visually dominant instead of being
  1/50th of a scroll. It is also what makes the wire cheap (§3.6) — the same
  grouping key serves both.
- **Skips are grouped by reason, not hidden**, and each carries who or what is
  responsible.
- **Rows stream in**, they do not appear all at once at the end: members exist
  as `pending` from the first frame and transition in place.
- **The DOM is bounded.** Collapsed groups render one row. An expanded group
  virtualises past 200 rows. A single device's full output opens in a drawer
  over HTTP (§3.6), never inline for all N.
- **Two retry actions, always both present**: **Retry failed** and **Retry
  skipped**. Retrying skipped is the one an operator reaches for most (four
  phones were busy; try them again now), and it is the one nothing in the
  product offers today for any bulk operation.
- **Every row links out**: "open this device's terminal" and, when truncated,
  "open in Monitor".

The same three-part summary (`ok / failed / skipped-with-reason`) and the same
two retry actions are used by the batch detail page, so a bulk install and a
fan-out command report identically (H3). That consistency is delivered as two
small shared components — `OutcomeSummary` and `SkippedGroups` — rather than by
merging the two mechanisms (§3.1).

### 3.16 Where the console lives, and how it relates to the terminal

- **`/console`** — a new top-level page in the `AppShell` nav. It is a fleet
  tool: a target picker (reusing the fleet page's filters and the existing
  `DevicePicker`), a command box with the saved-command list beside it, the
  History panel, and the report.
- **The device page's Terminal tab is unchanged in behaviour** and gains three
  things: the History panel (scoped to this device by default), the saved-command
  list, and a **"Run on more devices…"** action that opens `/console` with the
  command prefilled and this device preselected. The live shared transcript
  (plan 26 §3.8) stays exactly as it is — it is a different thing from a run
  report and should not become one.
- **The fleet page's selection toolbar** gains **Run command…**, **Push file…**
  and **Pull file…** beside the existing Install (F15). It attaches to whatever
  selection the page exposes and adds no selection mechanism of its own:
  **plan 91 owns moving selection into Wall view**, the cursor-anchored count
  badge, and double-click-to-focus (its F11–F13). If 91 lands first these
  actions appear on the Wall for free; if this plan lands first they are
  List-only until 91 arrives, and nothing has to be undone either way. Selecting
  every filtered device (a select-all, F16) is small enough to belong here and
  is built here, through the existing `useBulkSelection` hook rather than a
  fourth ad-hoc `Set`.

### 3.17 One entry point, not two

`POST /api/command-runs` is the only way to start a run — including from the
browser, including for N = 1 from the console. The WebSocket carries **events
only** (`command.started`, `command.progress`, `command.output`, `command.stage`,
`command.finished`) plus subscribe/unsubscribe.

This follows three existing precedents rather than inventing a fourth: the
transfer routes, the adb-endpoint routes and the readiness route all take the
browser's WS `clientId` in an HTTP body precisely because a manual lease's
holder *is* a WS session and HTTP has no native notion of one
(`api/transfer.ts:32-40`, `api/adb-endpoint.ts:22-35`). One entry point means
one authorisation path, one audit path, and one place to get the gate right.

`shell.exec` over WS stays exactly where it is — it is the interactive terminal
and it works (F1, F2). Step 93.5 makes it *record* through the same store so
history is one mechanism, without moving its transport. Studio must still
`GET` the run before subscribing, because `/ws` has no snapshot replay.

### 4.2 Schema (`packages/core/src/db/schema.ts` + one Drizzle migration)

```ts

  hash: z.string(),

  previewTruncated: z.boolean(),

  ok: z.number(), failed: z.number(), skipped: z.number(), cancelled: z.number(),

// ── server → client (events only — §3.17)
| { type: 'command.started';  payload: { runId, cmd, stages: number, members: CommandMember[], counts: CommandCounts } }

| { type: 'command.finished'; payload: { runId, status: CommandRunStatus, counts: CommandCounts, durationMs: number } }

| { type: 'command.unsubscribe'; payload: { runId: string } }
```

### 4.5 The runner (`packages/core/src/command-console/`, new)

> **Naming note for maintainers.** No identifier in this package may be named
> `console` — it shadows the global and produces a confusing failure at a
> distance. The directory is `command-console/`; the types are `CommandRun*`;
> the settings keys are `shell.fanout*`; the tables are `command_*`.

```ts
// runner.ts  ← the `Ships:` artefact
export interface CommandRunnerDeps {
  db: Db
  store: CommandRunStore
  leases: LeaseManager
  shellPortFor: (deviceId: string) => ShellPort
  resolve: (target: CommandTarget) => ResolvedCluster        // clusters/resolve.ts, reused
  settings: () => FarmSettings['shell']
  recorder: EventRecorder['record']                          // the device_events audit, unchanged
  audit: AuditLogger
  broadcast: (runId: string, msg: ServerMessage) => void      // to subscribers of THIS run only
  roleOf: (userId: string | null) => Role
  getDevice: (deviceId: string) => { ownerId: string | null } | null
  log: Logger
}

export interface CommandRunner {
  start(input: StartCommandRunInput): Promise<{ run: CommandRunInfo; members: CommandMember[] }>
  cancel(runId: string, actor: string | null): void
  continueRun(runId: string, actor: string | null): void
  /** Boot sweep: every non-terminal run becomes `cancelled` (§3.7, mirroring `failOrphanRunning`). */
  sweepOrphans(): number
  stop(): void
}
```

Execution, per member, in order:

```
1. admit    → checkInputAllowed; on `no_lease` acquireManual (purpose:'command')
              anything else → skipped, verbatim code+message, no exec
2. echo     → recorder.record({ stream:'input', kind:'shell.exec',
                                meta:{ cmd: redactShellCommand(cmd), runId } })
              — the SAME audit row the terminal writes, so a fan-out is not
                invisible on a device's Logs tab
3. exec     → shellPort.exec(cmd, { timeoutMs: shell.execTimeoutMs,
                                    maxOutputBytes: shell.fanoutMaxOutputBytes,
                                    signal })
4. record   → member row updated; outputHash = Bun.hash(exitCode+"\0"+stdout+"\0"+stderr)
              recorder.record({ kind:'shell.result', meta:{ exitCode, bytes, durationMs, runId } })
5. release  → releaseManual in a `finally`, only if THIS runner acquired it
6. emit     → queued into the 250 ms progress coalescer; a first-seen hash also
              emits one `command.output`
```

There is deliberately **no working-directory emulation** for a fan-out. Plan
26's per-device emulated cwd (§3.7 there) is a property of one operator's one
terminal session; a fleet command runs from the device's default and the run
form says so. Carrying twenty independent cwds into a fan-out would be state
nobody asked for and nobody could see.

The coalescer is one `setInterval(250)` per running run, cleared on finish —
not a global tick, so an idle core schedules nothing.

### 4.7 The archive writer (`packages/core/src/api/zip-stream.ts`, new)

A stored-only zip, ~150 lines, no dependency:

- Local file header + entry name + raw bytes + data descriptor, per entry.
- Central directory at the end (≈60 bytes per entry held in memory — 40 entries
  is under 3 KB).
- CRC-32 over each entry as it streams (a 256-entry table, computed once).
- No compression (method 0), no zip64 — the `transfer.maxArchiveBytes` cap of
  2 GiB keeps every offset inside 32 bits by construction.
- Entry names sanitised: no `..`, no absolute paths, no backslashes,
  NFC-normalised; duplicates get a ` (2)` suffix rather than silently
  overwriting.

Returned as a `ReadableStream` with `content-disposition: attachment`. Refuses
before the first byte when the summed `sizeBytes` exceeds the cap, so a browser
never receives a truncated archive.

## 6. Acceptance criteria

1. One command, typed once, runs on a selection, a cluster, a tag set, or every
   device, and returns one result per device with its own stdout, stderr and
   exit code — rendered exactly as the terminal renders one today.
2. Every device in the target that did not run the command appears in the report
   as `skipped`, carrying `checkInputAllowed`'s own code and message verbatim.
   No count anywhere in the report is unexpandable into a device list.
3. A device the operator already controls runs the command with no lease
   acquire and no lease release. An idle device is acquired and released exactly
   once, and is released even when the command throws.
4. A device controlled by someone else is skipped, naming them. A device running
   a job is skipped with `device_busy`. Neither is ever taken over.
5. `shell.mode: 'off'` refuses a fan-out for an admin. `shell.fanoutEnabled:
   false` refuses it independently of `shell.mode`. A new server-mode install has
   both off.
6. A fan-out of a high-consequence command to more than one device is refused
   without an explicit acknowledgement, and the acknowledgement is recorded on
   the run and in the audit log with the pattern that matched.
7. A staged run stops after stage 1, holds no lease while waiting, and continues
   or stops on the operator's word. Left waiting past `fanoutStageWaitSec`, it
   cancels itself.
8. Cancelling a 100-device run in flight leaves every not-yet-started member
   `cancelled` and starts none of them.
9. A 100-device run's live WebSocket payload stays under the 512 KB
   `MAX_BUFFERED` budget, and full per-device output is only ever fetched over
   HTTP.
10. On a homogeneous farm, a survey command's report collapses to a small number
    of groups, and a single non-zero exit sorts above every success.
11. History is durable across a page reload, a core restart, and a browser
    change; it covers commands typed in the device Terminal and commands fanned
    out from the console, in one list; and any entry can be re-run against the
    same or a new target.
12. A saved command is visible to the whole farm, editable only by its owner or
    an admin, cannot be created by someone who could not run it, and prefills
    its default target without enforcing it.
13. `POST /api/batches` and `POST /api/jobs` with `internal:install`,
    `internal:push` or `internal:pull` are refused without `device.files`
    (as widened by `shell.mode`) and with `transfer.enabled: false`.
14. Bulk push, bulk pull and bulk install each report per device, cancel, retry
    only the failed, and retry only the skipped — through the same components.
15. A bulk pull across N devices produces N artifacts, each linked to its
    pulling job; the batch page lists them grouped by filename; and **Download
    all** returns one archive whose entries cannot collide across devices.
16. `transfer.progress` is delivered only to viewers of the device it concerns.
17. A core restart during a run leaves the run `cancelled` with every unfinished
    member explained, never `running` forever.
18. `/api/adb/stats` reports the `commandConsole` block, and the §7.3 ladder is
    filled in for 5, 20 and 100 devices.
19. `bun run typecheck`, `bun test`, and `bun run --cwd packages/studio test`
    are green. `bash scripts/check-plan-status.sh` passes.

## 8. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Per-member lease acquire/release floods `lease.changed` on a 100-device run (H4). | `Lease.purpose: 'command'` makes the badge honest rather than alarming; §7.3 measures the rate. **Designed, not executed:** if it bites, the runner coalesces — emit `lease.changed` only for holds exceeding 1 s, and one aggregate `command.holding` for the rest. Executed only on a number from the ladder, and recorded either way (the failure mode plan 85 §8 names: a conditional step that never gets built because the rung never runs). |
| The dispatch gate breaks an existing workflow that relied on `job.run` alone. | It is a real privilege reduction and is called out in the release notes. Mitigation is a permission grant, not a bypass: an operator who should install APKs gets `shell.mode: 'operator'`, which is the switch that already exists for exactly this. The regression watch pins the admin path. |
| The report's grouping hides a device-specific problem inside a large group. | Grouping is by *exact* output including the exit code, so a device that differs at all is never in the same group. Groups always show their device count and expand. Ordering puts non-`ok` groups first regardless of size. |
| 32 KB × 100 members × 500 runs per user is real disk. | Two independent bounds: `retention.commandRunDays` (14) and `commandRunsPerUser` (500, trimmed on insert). Both are settings; the retention sweep is not gated by `retention.enabled`, for the reason `eventInputDays` already is not. |
| A fan-out on a busy farm starves interactive work by saturating the exec semaphore. | It cannot exceed the semaphore, which is the same budget everything else shares and which autoscales (F23). `shell.fanoutConcurrency` gives an operator a lower ceiling; §7.3 records control-reply p95 *during* a run so the cost is a number. |
| The acknowledgement is mistaken for a security control. | It is described as an audit fact in the code comment, the API error text, the spec and this plan, using the same wording plan 26 §3.4 established. Any client can send it, and that is stated where it is implemented. |
| Two mechanisms (console runs, batches) look to a user like two products. | They share the report components, the skipped-with-reason discipline and both retry actions (§3.15), and the console's **Run on more devices…** and the fleet toolbar reach both from the same place. §3.1 records the boundary so it is not re-litigated by accident. |
| The zip writer has a subtle bug and produces archives that open on macOS but not Windows. | Stored entries with a central directory is the most conservative zip that exists; the size cap keeps every offset in 32 bits so zip64 is never needed; unit tests read the output back independently; the ladder opens one by double-click on both platforms. |
| A saved command referenced by a plan-94 schedule is deleted. | Deletion is a real delete and the id becomes dangling by design (§3.10). Plan 94 owns the dangling-reference behaviour; this plan guarantees only that the id is stable and that `command_runs.saved_command_id` is provenance, never a foreign key. |
| `shell.fanoutEnabled` defaulting `true` on loopback surprises someone. | It is exactly `shell.mode`'s existing asymmetry (F25), the gate above it is unchanged, and a loopback install is a single-user tool by definition. A server-mode install gets `false`, which is the case where the surprise would matter. |

## 9. Open questions — owner decisions

1. **Should a fan-out be allowed to take over an idle device that another
   operator released seconds ago?** Today `acquireManual` on an idle device
   simply succeeds (F19), and plan 71 §3.7 added a *quiet period* for jobs
   precisely so a job does not snatch a device out from under someone who
   stepped away. This plan does **not** apply that quiet period to console
   members, on the grounds that a fleet command is an interactive act by a
   person and waiting 10 s per device would make a 100-device survey
   unusable. If the owner would rather a colleague's just-released device be
   left alone, the change is one call to the same helper the scheduler uses —
   but it must be a decision, not a default.

2. **Should `shell.fanoutEnabled` default `true` on a loopback install
   (§3.8), or `false` like `shell.endpointEnabled` (F25)?** The plan chooses
   `true`, following `shell.mode`'s asymmetry, so the feature the owner asked
   for works out of the box on a laptop farm. The counter-argument is real:
   fan-out is a strictly bigger surface than a single gated shell, and the
   endpoint's own comment says a bigger decision "should never be a
   discovery". Server mode is `false` either way.

3. **Is grouping identical results the right default (H1), or should the
   report be a flat per-device table with grouping as a toggle?** Grouping is
   right for a homogeneous rack farm and wrong for a farm of twenty different
   models running twenty different builds. The plan defaults to grouped and
   records the distinct-output ratio on every run, so the answer becomes a
   measurement rather than a preference — but the default at ship time is a
   product call.

4. **Should history be visible to the whole team by default?** §3.9 makes
   your own history the Studio default and lets admins see everyone's, on
   plan 26 §3.8's reasoning that seeing what a colleague just ran explains a
   device's behaviour. An alternative reading is that a command line is
   personal working notes. The stored command is redacted either way, and the
   `device_events` audit is unchanged whichever way this goes.

5. **How long should a bulk pull's collected files live?** They are ordinary
   artifacts, so they are swept by `retention.maxAgeDays` — which is
   **`enabled: false` by default**, meaning today they live forever. That is
   fine for a laptop and wrong for a farm pulling screen recordings nightly.
   Whether bulk-pull artifacts deserve their own, always-on budget (like
   events and command runs) or should stay under the opt-in artifact policy is
   a storage-policy decision, not a technical one.

6. **Should a fan-out reach a device that is being *assisted* (plan 91), or a
   device a job is running on?** Plan 91's answer for its own scope is a firm
   no — its §1 states that `shell.exec` stays lease-holder-only "and a test
   proves it" — and this plan follows it (§3.8). The practical consequence is
   worth the owner seeing plainly: on a farm where jobs run continuously, a
   fleet command will routinely skip a meaningful fraction of the farm with
   `device_busy`, and **Retry skipped** is the intended answer rather than a
   workaround. If that turns out to be the wrong trade in daily use, the
   change is one branch in `admitMember` plus a farm setting — but it would be
   a deliberate widening of spec §11.3's trust boundary, and it must be the
   owner's decision, not a convenience added later by whoever hits the
   friction first.

7. **Should a console run be resumable after a core restart?** §3.7 says no,
   deliberately: silently resuming commands at a farm after a restart, with
   nobody attached, is the opposite of what an interactive act means. The
   counter-case is a 100-device `pm uninstall` that got 60% through. The
   plan's answer is that such work belongs in a batch or a schedule (plan 94),
   but if the owner wants resumable console runs the store already has
   everything needed and only the boot sweep would change.
