Written from the code, not from the request. Every claim below is either
**CONFIRMED** (a file and a line say so, or a command was run and its output

— a solid black wallpaper with the name and the number centred on the phone's

## 1. Goals

- **Every farm device has a short number**, assigned once, incrementing, stable
  for the life of that hardware — including across Forget and re-admit — and
  overridable by the operator with a collision that is refused loudly rather
  than resolved silently.
- **The number is where a number is useful**: the wall tile, the list row, the
  device page header, the device picker, the log line, the device event, the
  doctor output, and the sort order of the fleet list. Not just in the database.
- **A phone on a rack says what it is.** A solid black wallpaper carrying the
  device's name and its number, on both the home screen and the lock screen,
  large enough to read at arm's length.
- **One image per device, correct for that device's panel**, with no host-side
  image library, no bundled font, and no per-device asset stored or pushed.
- **Labelling is honest about what it achieved.** A device whose label could not
  be applied reads `unavailable` with a reason, and a device where only half of
  it took reads `partial` naming which half — never a green tick the phone does
  not actually show. This is the rule `farm-tag.ts` already states for the
  device-under-automation marker, applied to a second thing an operator will
  otherwise trust wrongly.
- **The operator's own wallpaper is not silently destroyed.** Labelling is
  opt-in, it says plainly what it will overwrite, it attempts to capture the
  original once, and it never offers to restore something it did not capture.
- **Removing a device removes its label**, best-effort, before the row goes —
  the same ordering, and the same failure discipline, as the network route
  already has.
- **A restored backup cannot hand two phones the same number.**

## 2. Non-goals

- **Not a host-side image renderer.** §3.4 argues this at length: the encoder is
  cheap (F12) and the font is not (F11), the device already has both, and a
  host-rendered PNG still could not be *set* without the agent (H1). Building
  one would buy a preview and a dependency-shaped hole.
- **Not the guest agent's Kotlin side.** Plan 90 owns the APK. This plan
  specifies the wire contract it needs (§4.5) and refuses honestly until it
  exists.
- **Not driving the wallpaper chooser with input injection.** `ATTACH_DATA`
  opens a per-OEM dialog that would need a lease, a live session, an inspector,
  and a different tap sequence per skin — the definition of "asal jalan aja".
  Rejected in writing so nobody proposes it again in six months.
- **Not a periodic label sweep.** Reconciliation happens on reconnect, on
  change, and on demand (§3.7). A timer that pokes every device forever to
  re-check a thing that changes twice a year is cost with no event behind it.
- **Not a rack-position model.** Numbers are identity, not location. Shelf/row
  coordinates are a tag problem (`device_tags` already exists) or a §9 question,
  not a second identifier.
- **Not renaming or restructuring `label`.** It already works (F5). §3.3 says
  only what changes about how it is *composed* with the number.
- **Not a change to admission.** Whether a phone joins the farm stays a human
  decision (plan 56). This plan only decides what happens *after* it joins.

## 3. Context and design decisions

### 3.1 "On first connection" has to mean "on admission", and that is better

The owner's decision is that the number is assigned incrementally on first
connection. Read literally against this codebase, that is the wrong hook, and
the reason is worth stating because it is not obvious.

A phone that connects to adb does **not** become a device (F2, spec §7.5). It
lands in the Discovered tray and waits. The adb server is routinely shared with
Android Studio, with a developer's own phone, with whatever is plugged in to
charge — that is the entire reason admission exists. Numbering at the literal
first connection would hand `#7` to a colleague's phone that spent ninety
seconds charging, burn the number permanently (§3.2 keeps numbers), and leave a
gap in the rack's sequence that nobody can explain.

**Decision.** The number is allocated inside `admitDevice()` — the one place a
`devices` row is created (F2) — in the same transaction as the insert. For the
operator this is indistinguishable from "on first connection": a phone gets its
number the first time it becomes theirs, in the same click. The Discovered tray
deliberately shows no number, exactly as it deliberately shows no status, no
cluster and no readiness (`packages/protocol/src/device.ts:100-108` makes this
argument already, for the same reason).

### 3.2 Forget then re-admit keeps the old number

Both answers are defensible, which is why this needs an argument rather than a
preference.

**Decision: the number is a reservation on `stableId`, and it survives Forget,
Block, unblock, and re-admission. It is released only by an explicit operator
action.** Five reasons, in descending weight:

1. **The number is written on the phone.** That is the whole point of this
   plan. A number that changes on re-admit means the wallpaper was lying for
   however long the device sat in the tray, and — worse — a physical sticker
   an operator put on the back of the case is now wrong, permanently and
   silently. Nothing in the system can detect that or fix it.
2. **`stableId` is already the repo's identity anchor for exactly this
   scenario.** `blocked_devices` and `discovered_devices` are both keyed on it
   and both say, in their own comments, that this is so they survive a
   forget/re-enroll cycle (F7). A third `stableId`-keyed table that behaved
   differently would be the odd one out, and the surprise would land on
   whoever reads the schema next.
3. **Forget is not a terminal verb here.** Plan 56 deliberately made it
   *non-*terminal: it returns a phone to the tray precisely so an operator can
   remove a device from the farm without declaring it permanently unwelcome
   (F6, spec §7.5). It gets used for ordinary things — clearing bad state,
   re-admitting into a different cluster, undoing a bulk mistake. Renumbering on
   every one of those makes an ordinary action expensive.
4. **Exhaustion is not real.** The counter advances only for genuinely new
   hardware. A hundred phones re-admitted a hundred times each still ends at
   `#100`. The "numbers get long" objection describes a farm that has churned
   thousands of *distinct* phones, at which point three digits is the least of
   its problems.
5. **The opposite answer's real motivation — "I want my numbers compact" — is
   better served by an explicit verb than by an inference.** So this plan gives
   it one: a per-device **Release number**, and a fleet-wide **Renumber**
   compaction that reassigns `1..n` in list order **and re-pushes every label in
   the same operation**, so a compaction can never leave a phone displaying a
   number that has moved. Block's dialog offers "also release its number" as an
   unchecked box, because block is the one verb that genuinely means *never
   again*.

The consequence to accept: the fleet list can show `#3, #7, #8, #15` on a
twelve-phone farm. That is honest — those gaps are phones that used to be here —
and the Renumber action is one click away when it stops being useful.

### 3.3 The number and the name compose; the number never enters the name

`label` already does its job (F5): it defaults to the probed model and the
operator can rename it. The temptation is to change the default to
`"${model} ${number}"` so the existing tiles become distinguishable with no
other work.

**Decision: do not.** A number embedded in a free-text, user-editable string is a
second source of truth for the number, and it desynchronises the first time
anyone renames or renumbers. That is precisely the drift this repo's
conventions exist to prevent, and `settings.ts:226-231` makes the same argument
about `DeviceSettings` and `FarmSettings.defaults`.

The default label stays the probed model. The number is its own field, rendered
*beside* the label everywhere, number first:

```
#7  Pixel 5
```

Number first because it is the key an operator scans for, and because a column
of right-aligned numbers is scannable in a way a column of identical model
names is not. On the phone's own screen the owner's layout wins verbatim: the
name on top, the number below it, the number much larger (§4.4).

### 3.4 The image is rendered on the device, and the host ships no encoder

This is the decision the rest of the wallpaper design hangs on, so it gets the
full argument.

**Could the host generate the PNG?** Yes, and cheaply. F12 is not a guess: a
40-line encoder using only `Bun.deflateSync`, `Bun.hash.crc32` and
`Bun.hash.adler32` produced a valid 720×1600 PNG in **2055 bytes**, verified
with `file` and `sips`, in this environment. Adding sharp or jimp to a project
that ships as one compiled binary would be indefensible when the primitives are
already in the runtime.

**So why not?** Three reasons, and the third is decisive:

1. **The encoder is not the hard part; the font is.** F11: there is no font
   file, no glyph data, and no rasteriser in this workspace. Drawing
   `Pixel 5` requires either bundling a font and a shaper (a real dependency,
   plus licence review in a repo that maintains `LICENSES.md` deliberately) or
   hand-authoring a bitmap font — which works for `[A-Z0-9]` and silently
   fails the moment an operator names a phone `Pixel 5 (弐)` or in Thai. A
   labelling tool that cannot render the name the operator typed is a
   half-feature.
2. **Per-device geometry becomes free.** F21: the core already knows every
   device's `screenW`, `screenH` and `density`. But if the host renders, it must
   also *store* and *push* one bitmap per device — through `TransferService`,
   whose source must be a server-side artifact id, never a path (F22) — which
   means an artifact row, a file on disk, and retention/GC interactions, per
   device, per rename. If the device renders, there is no image anywhere on the
   host at all. The answer to "one scaled image or one per device?" becomes
   **one per device, always, at zero storage cost** — which is also the right
   answer visually, because a single image scaled from 1440p to 720p is either
   soft or wrong-sized.
3. **A host-rendered PNG still cannot be set.** H1: setting a wallpaper needs an
   app process holding `SET_WALLPAPER`. If the agent has to be involved anyway,
   handing it two strings instead of a two-kilobyte PNG is strictly less
   machinery on both sides.

**Decision.** The host sends `{ name, number }` as text. The agent renders with
Android's own `Canvas`/`Paint` at the device's exact pixel dimensions and calls
`WallpaperManager`. No encoder, no font, no artifact, no push, full Unicode,
per-panel correctness. **The dependency-free PNG encoder is designed and
deliberately not built** — F12 is recorded so that if a future plan needs one
(a preview served as an image, say), it starts from a proven approach rather
than from a dependency.

Studio's preview of the label is HTML and CSS in the browser, which needs
nothing from any of this.

### 3.5 Two tiers, no silent fallback

**Tier 1 — the wallpaper (needs the guest agent).** A `screen-label` capability
on the agent, a `label.apply` verb, one bitmap set with
`FLAG_SYSTEM | FLAG_LOCK`. This is the feature the owner asked for.

**Tier 0 — lock-screen text (plain adb, no agent, no image).** H2:
`settings put secure lock_screen_owner_info "#7 Pixel 5"` plus
`lock_screen_owner_info_enabled 1`. If it works, it puts the identity on the
exact surface you read on a rack of sleeping phones, with no APK, no font, no
image, and — unlike the wallpaper — a **genuine** capture-and-restore, because
`settings get secure lock_screen_owner_info` reads back what was there before.
It costs one settings write. It is worth having on its own merits, and it is
what a device without the agent gets.

**Decision: these are two selectable modes, not a fallback chain.** A device set
to `wallpaper` on a phone with no `screen-label` capability reports
`unavailable` with the reason and Studio offers a one-click switch to
`lock-screen`. It does **not** quietly degrade. This is the rule the network
layer already follows — `vpn-helper` deliberately does not advertise a `probe`
capability and is therefore reported `unverified`, never `ok` (CLAUDE.md, spec
§7.9) — and the reason is the same: an operator who believes twenty phones are
labelled and finds three are not has been harmed more than one who was told.

A third possibility, `cmd wallpaper` (H1), is probed in 89.5 before anything is
built. If some Android versions do expose it, it becomes tier 0.5 and the design
above absorbs it as one more mode.

### 3.6 The wallpaper is device state, not session state — and that is a departure

F18 is the house pattern: `wake.ts`, `orientation.ts` and `farm-tag.ts` all
apply at session start and revert at session close, and the revert must be
stateless and idempotent. It would be easy, and wrong, to copy it here.

**The whole point of this feature is the phone nobody is looking at.** A label
that exists only while a session is open is absent exactly when the operator is
standing in front of the rack trying to find a phone. Session scope would
produce a feature that demos perfectly and is useless.

**Decision: labelling is device-scoped, persistent state**, in the shape
`devices.networkRoute` already established (F20) rather than the shape
`prep.rotation` established. There is precedent for both halves of this: F19
shows `wakeDevice` already running with no session at all, driven by the
readiness manager.

The idempotence rule still binds, and binds harder, because a device-scoped
apply has no `close()` to guarantee a matching revert:

- `label.apply` is keyed by a **fingerprint** (§4.4). Applying the same
  fingerprint twice is a no-op that still returns the device's current state.
- `label.clear` always performs the same writes regardless of how many times it
  is called — restore the captured original if one exists, otherwise clear to
  the system default — and consults no "have I already cleared" flag. This is
  `orientation.ts:61-68`'s rule verbatim, and `farm-tag.ts:62-67`'s.
- Neither operation reads or writes any in-memory "already applied" state. The
  device's own reported fingerprint is the only source of truth, which is what
  makes a core restart mid-apply harmless.

### 3.7 Reconciliation: on reconnect, on change, on demand — and nothing else

Four moments, each with an event behind it:

1. **`onDeviceReady`** (`daemon.ts:2173`) — the same hook `restoreNetworkRoute`
   already uses, and probe-first for the same reason (F20): ask `label.status`
   for the device's fingerprint, and re-apply only when it differs from the
   stored one. A phone that already carries the right label costs one cheap
   round trip and no render.
2. **A rename or a renumber** — `PATCH /api/devices/:id` touching `label` or
   `number`, debounced 2 s so a person typing a name does not fire six renders.
3. **An explicit action** — "Re-apply label", and the fleet-wide "Apply labels"
   for turning the feature on across an existing farm.
4. **Forget and Block** — best-effort clear *before* the row is deleted, in the
   same position and with the same failure discipline as `releaseRoute`
   (`lifecycle.ts:181-198`): a failure is logged and recorded, and never aborts
   the removal, because refusing would rebuild the trap plan 56 removed.

**Not** on session start (the point is idle phones), and **not** on a timer
(§2). Drift — someone changing the wallpaper on the phone by hand — is caught
by the reconnect probe, which is when it matters, since a device that never
disconnects is a device nobody is confused about.

Concurrency: `labelling.maxConcurrent` (default 2) bounds simultaneous applies
farm-wide, for the same reason `adb.maxInstallConcurrent` exists — twenty
devices reconnecting at once must not start twenty agent round trips over one
USB controller (plan 85 §3.4).

### 3.8 Opt-in, with one switch for a real farm

The wallpaper overwrites something an operator may care about, and H3 says we
probably cannot put it back.

**Decision: `labelling.mode` defaults to `off`**, per device, and the default is
inherited from `FarmSettings.defaults` at admission exactly like every other
device setting (F26) — so an operator running an actual rack sets the farm
default to `wallpaper` once, and every phone admitted afterwards is labelled
with no further thought. Existing devices are covered by the explicit fleet
action, not by magic: flipping a farm default has never retroactively changed
existing devices in this codebase and should not start here.

The admit dialog gains one checkbox reflecting the farm default, and the copy
next to it says what it does without softening it: *"Replaces this phone's
wallpaper with a black label. Enkaku will try to save the current one first,
but on many Android versions it cannot read it back — if that fails, turning
labelling off restores the system default wallpaper, not the original."*

## 4. Technical design

### 4.1 Schema (`packages/core/src/db/schema.ts`)

```ts
/**
 * A device's short, human-facing number (plan 89 §3.1, §3.2).
 *
 * Keyed on `stableId`, NOT on `devices.id`, for the same reason
 * `blocked_devices` and `discovered_devices` are: the reservation must
 * survive a Forget/re-admit cycle, a different USB port, and a switch to
 * adb-tcp. A number is printed on the phone's own screen and, very often, on
 * a sticker on the case — a number that silently moved is worse than no
 * number at all.
 *
 * Released only by an explicit operator action (`DELETE /api/devices/numbers/
 * :stableId`, or the fleet-wide compaction), never by Forget and never by
 * Block.
 */
export const deviceNumbers = sqliteTable('device_numbers', {
  stableId: text('stable_id').primaryKey(),
  /**
   * UNIQUE is the guarantee, not the arithmetic in `allocateDeviceNumber`.
   * A duplicate is a loud constraint violation, never two phones showing #7.
   */
  number: integer('number').notNull().unique(),
  assignedAt: integer('assigned_at', { mode: 'timestamp' }).notNull(),
  /** null = allocated automatically; a user id = an operator set it by hand (§4.3). */
  assignedBy: text('assigned_by'),
})

/**
 * Monotonic counters this codebase owns. One row today (`device_number`).
 * A table rather than a column because SQLite AUTOINCREMENT needs an INTEGER
 * PRIMARY KEY and `devices.id` is a text UUID (F3).
 */
export const sequences = sqliteTable('sequences', {
  name: text('name').primaryKey(),
  next: integer('next').notNull(),
})
```

`devices` gains two columns, both nullable, both about the *applied* label —
never about the number itself, which lives above:

```ts
/**
 * The label fingerprint this device is believed to be displaying (§4.4), or
 * null when nothing has been applied. Compared against the agent's own
 * reported fingerprint on reconnect; a mismatch is the only trigger for a
 * re-render. Deliberately a cache of the device's answer, never the source
 * of truth — the device is.
 */
labelFingerprint: text('label_fingerprint'),
/**
 * What happened the last time a label was applied, as JSON
 * (`DeviceLabelStateSchema`): mode, state, reason, originalCaptured,
 * appliedAt. Never trusted over a live `label.status`; this exists so the
 * fleet list can render a truthful badge without N round trips.
 */
labelState: text('label_state', { mode: 'json' }),
```

### 4.2 The allocator (`packages/core/src/registry/device-number.ts`, new — the plan's `Ships:` artefact)

```ts
export interface AllocatedNumber {
  number: number
  /** false when this stableId already had a reservation — the sticky path (§3.2). */
  fresh: boolean
}

/**
 * Allocates (or re-uses) a device's number, inside the CALLER's transaction.
 *
 * Correctness under concurrent first-connections rests on three things, in
 * descending order of how much weight they carry:
 *
 * 1. `device_numbers.number` is UNIQUE. Whatever else is wrong, two phones
 *    cannot end up displaying the same number — the insert fails instead.
 * 2. `next = max(storedWatermark, max(number) + 1)`. The stored watermark is
 *    the fast path; the `max()` is the defence. It is what makes a restored
 *    backup safe (a watermark that went backwards cannot re-issue a number
 *    that is still reserved), and it is what makes a manual override above
 *    the watermark safe (§4.3) without a second bookkeeping step.
 * 3. `bun:sqlite` is synchronous on one connection and the data directory is
 *    single-owner-locked (F28), so nothing can interleave inside this
 *    transaction body. This is the reason the code looks naive; it is not
 *    the reason it is correct, which is (1).
 *
 * Callers MUST already be inside a transaction — `admitDevice` is, so that a
 * failed insert cannot consume a number.
 */
export function allocateDeviceNumber(
  tx: Db,
  stableId: string,
  opts?: { assignedBy?: string | null },
): AllocatedNumber

/** The reservation for a stableId, or null. Never allocates. */
export function lookupDeviceNumber(db: Db, stableId: string): number | null

/** stableId → number for a whole fleet, in one query (never N+1, plan 19 §4.3's rule). */
export function loadDeviceNumbers(db: Db): Map<string, number>

/**
 * Sets a number by hand. Throws `E_NUMBER_TAKEN` naming the current holder
 * — a collision is refused, never resolved (§4.3). Advances the watermark
 * past `n` so the next automatic allocation cannot collide with it.
 */
export function setDeviceNumber(db: Db, stableId: string, n: number, actor: Actor): void

/** Explicit release (§3.2). The number becomes available to the compaction below, not to the next allocation. */
export function releaseDeviceNumber(db: Db, stableId: string, actor: Actor): void

/**
 * Reassigns 1..n across every current farm device in `label ASC, id ASC`
 * order, and returns the devices whose number changed so the caller can
 * re-push their labels in the SAME operation. A compaction that renumbered
 * without re-labelling would leave phones displaying numbers that moved,
 * which is the one outcome §3.2 exists to prevent.
 */
export function compactDeviceNumbers(db: Db): { stableId: string; from: number; to: number }[]
```

`admitDevice` (`packages/core/src/registry/admission.ts:92-120`) wraps its
insert and its `discovered_devices` delete in a `db.transaction` — today they
are two loose statements — and calls `allocateDeviceNumber` inside it.

### 4.4 The label itself: fingerprint, layout, geometry

**Fingerprint.** One string, computed on the host, that changes if and only if
what the phone should display changes:

```
fingerprint = sha256([
  mode,              // 'wallpaper' | 'lock-screen'
  number,            // '7'
  showName ? name : '',
  rendererVersion,   // an integer the AGENT reports — bump it in plan 90 when
                     // the drawing changes, and every device re-renders once
  `${screenW}x${screenH}`,
].join('\n')).slice(0, 16)
```

Geometry is in the fingerprint because a device whose `wm size` changed (a
resolution override, a redroid instance resized) needs a fresh render.
`density` deliberately is **not**: see below.

**Layout**, the owner's specification made precise:

```
┌─────────────────────────┐   background: pure black (#000000)
│                         │   text:       pure white (#FFFFFF)
│                         │
│        Pixel 5          │   name:   cap height  7% of min(w,h), regular
│                         │
│           7             │   number: cap height 22% of min(w,h), bold
│                         │
│                         │
└─────────────────────────┘
```

- **Sized as a fraction of the panel, not in dp.** This is the counterintuitive
  part and it is deliberate: the operator is reading from a metre away, so what
  matters is how much of the screen the glyph occupies, not its physical
  millimetres. A 720p phone and a 1440p phone therefore show a number of the
  same *apparent* size. `density` (F21) is consequently unused, which is worth
  a comment in the code so nobody "fixes" it later.
- **Centre-safe.** All text is constrained to a centred square of side
  `min(w,h) × 0.8`. Android crops a wallpaper toward the centre when the
  orientation changes, so **one bitmap serves both orientations** — there is no
  second landscape image, and `prep.rotation` (plan 85 §3.7) needs no
  interaction with any of this. A device locked to landscape shows the same
  label, cropped, still centred.
- **The number is large enough to survive partial occlusion** by a launcher's
  icon grid (H4). At 22% of the short edge, a single digit is roughly 150 px
  tall on a 720p phone; a row of icons covering half of it still leaves it
  readable.
- **`showName: false`** drops the name and raises the number to 32%, for
  operators who want maximum legibility and read the name in Studio.

**Sanitisation.** The name is truncated to 24 grapheme clusters and stripped of
control characters and newlines before it goes on the wire. The agent draws
whatever it is given; it is the host's job not to give it a novel. A name that
does not fit the centre-safe square is ellipsised by the agent, which is the
only party that can measure it.

```ts
    fingerprint: string,      // opaque to the agent; echoed back verbatim
    number: string,           // already formatted, e.g. '7'
    name: string | null,      // null = number only
    surfaces: ('home' | 'lock')[],
} }
// ← result
{ applied: ('home' | 'lock')[],   // what ACTUALLY took — the source of `partial`
  fingerprint: string,
  rendererVersion: number,        // bump → every device re-renders once
  widthPx: number, heightPx: number,
  wallpaperIdHome: number | null, // WallpaperManager.getWallpaperId(FLAG_SYSTEM)
  wallpaperIdLock: number | null }

// → label.status  (params: {})
// ← result
{ fingerprint: string | null,     // what the agent last applied
  matchesOurs: boolean,           // its stored id still equals the live one
  wallpaperIdHome: number | null,
  wallpaperIdLock: number | null,
  originalCaptured: boolean,
  rendererVersion: number }

// → label.clear  (params: { restoreOriginal: boolean })
// ← result

  fingerprint: null }
```

**Five behavioural requirements**, each of which this plan's honesty rules
depend on:

1. **`applied` reports what took, not what was attempted.** An OEM skin that
   swallows the lock-screen half (H5) must produce `applied: ['home']`, so the
   core can report `partial` instead of `applied`.
2. **`label.apply` with an unchanged fingerprint is a cheap no-op** that still
   returns the current ids — this is what makes §3.7's reconnect probe free.
3. **The agent captures the original wallpaper once**, on its very first apply,
   and reports `originalCaptured` honestly. If `getWallpaperFile` throws or
   returns nothing (H3, a live wallpaper, an API-level restriction), that is
   `false` — never an optimistic `true`, and never an error that blocks the
   apply.
4. **`label.clear` is idempotent** and consults no "already cleared" flag: it
   performs the same writes on the tenth call as on the first, and reports which
   of the two things it did.
5. **`rendererVersion` is an integer the agent owns.** Changing the drawing
   without bumping it leaves every device displaying a stale label that the
   fingerprint says is current.

**A dependency worth naming out loud:** F17 — today the agent is installed only
as a side effect of applying a network route. A farm that never configures a
proxy has no agent on any phone, so `wallpaper` mode would be `unavailable`
everywhere. Plan 90 making the agent a first-class, independently-installable
component is therefore a **hard prerequisite** for tier 1, not a nicety. Tier 0
(§3.5) is what makes this plan useful before that lands.

## 6. Acceptance criteria

1. Every admitted device has a number; numbers increment from 1 and are never
   duplicated, enforced by a UNIQUE constraint and not only by arithmetic.
2. Forget followed by re-admit returns the **same** number. Block, unblock, and
   re-admit also return the same number.
3. An explicit release frees a number; nothing else does.
4. A manual number that is already taken is refused with 409 naming the holder,
   and the next automatic allocation never collides with a manually-set one.
5. Restoring an older backup cannot issue a number that is still reserved —
   `max(number) + 1` covers a watermark that went backwards.
6. Compaction renumbers `1..n` in list order and re-applies every affected
   device's label in the same operation, reporting any that failed.
7. The number appears on the wall tile, the device card, the device page header,
   the device picker, every device-naming log line, the device events, the
   doctor output, and the fleet list's default sort.
8. A discovered device shows no number anywhere, and the admit toast names the
   number it was actually given.
9. With `labelling.mode: 'wallpaper'` and an agent advertising `screen-label`, a
   phone displays a black wallpaper with its name and number on **both** the
   home and lock screens, sized per §4.4 and centred.
10. The same bitmap reads correctly in both orientations, including on a device
    locked by `prep.rotation`. There is exactly one image per device and none on
    the host.
11. A device whose agent lacks `screen-label` reads `unavailable` with a reason.
    It is never silently downgraded and its wallpaper is never touched.
12. A device where only one surface took reads `partial` naming which. It is
    never reported as `applied`.
13. Applying the same fingerprint twice performs no work the second time.
    `clear` performs identical writes however many times it is called, and
    consults no "already done" flag.
14. `originalCaptured: false` means Studio never offers "Restore original", and
    the clear confirm says it will reset to the system default.
15. `labelling.mode` defaults to `off`; the farm default is inherited at
    admission only; existing devices change only via the explicit fleet action.
16. Forget and Block clear the label before deleting the row; a failure is
    logged and recorded and never blocks the removal.
17. Reconnecting a correctly-labelled device costs one status call and no
    render. Concurrent applies never exceed `labelling.maxConcurrent`.
18. `mode: 'lock-screen'` works on a phone with **no guest agent installed**, and
    turning it off restores the prior owner-info text exactly.
19. §0.2's H1 and H2 have been replaced by CONFIRMED rows carrying real command
    output.
20. `bun run typecheck`, `bun test`, and `bun run --cwd packages/studio test` are
    green. `bash scripts/check-plan-status.sh` passes.

## 8. Risks and mitigations

| Risk | Mitigation |
|------|-----------|
| Plan 90 slips and tier 1 never lands. | Phase A (89.1–89.4) and 89.7 ship without it and are independently useful: numbers everywhere, plus lock-screen text on a phone with no APK at all. The plan is sequenced so the agent dependency is the *last* thing needed, not the first. |
| The original wallpaper cannot be restored (H3). | Never promised. Capture is attempted once and its outcome is a field every surface branches on; the opt-in copy says so before anything is overwritten. |
| An OEM skin swallows the lock-screen wallpaper (H5). | The agent reports what actually took; the core reports `partial` naming the missing half. §7.3 tests three skins explicitly. |
| Sticky numbers grow unbounded on a high-churn farm. | Only genuinely new hardware advances the counter (§3.2 point 4). An explicit Renumber compaction exists, and it re-pushes labels so it can never desynchronise the phones. |
| Compaction renumbers phones whose labels then fail to re-push, leaving stale numbers on screens. | The compaction response lists every device whose re-apply failed, and Studio shows them as `stale`. The reconnect probe fixes them on their own; the fleet action fixes them now. |
| A restored backup issues a duplicate number. | `max(number)+1` guards the watermark, and UNIQUE guards the arithmetic. Acceptance criterion 5 tests it directly. |
| Twenty devices reconnecting at once start twenty agent round trips. | Probe-first means a correctly-labelled device costs one cheap status call; `labelling.maxConcurrent` (default 2) bounds the rest, the same reasoning as `adb.maxInstallConcurrent` (plan 85 §3.4). |
| Someone later "optimises" the renderer to use `density`. | §4.4 states in the code comment why the sizing is a fraction of the panel and not a physical unit: the operator reads from a metre away. |
| A very long or right-to-left device name breaks the layout. | The host truncates to 24 graphemes and strips control characters; the agent ellipsises what still does not fit, because it is the only party that can measure. |
| The label makes a phone look "managed" to an app on it. | It is a wallpaper. It carries no more information than the device-under-automation property already discloses deliberately (spec §9.4, `farm-tag.ts`), and unlike that property it is not readable by an app at all. |
| Adding a labelling call to `onDeviceReady` slows device readiness. | It is fired-and-tolerated exactly like `restoreNetworkRoute` beside it (`daemon.ts:2173-2181`), never awaited on the readiness path. |

## 9. Open questions

These are product decisions. This plan does not make them.

1. **Should the number carry a prefix?** A single-rack farm reads `#7` fine; a
   three-rack farm may want `A7`, `B12`. A farm-wide `labelling.prefix` string
   would cost almost nothing and would change the fingerprint and every
   wallpaper. Deliberately not built: it is a naming decision, and a wrong
   default would be baked into a hundred phones' screens.
2. **Should `Block` release the number by default?** §3.2 says no, and offers an
   unchecked box. The argument for yes — block genuinely means never again — is
   real; the argument against is that a blocked phone may be unblocked and is
   still the same phone. The unchecked box is this plan's compromise, not a
   ratified answer.
3. **Should the number be visible to a script or an agent?** `ctx.device` today
   exposes identity, not presentation. A script that logs "finished on #7"
   reads better than one that logs a UUID. Cheap to add; deliberately not added
   here, because it widens the SDK surface for a cosmetic reason.
4. **What should a redroid or cloud-node device show?** It has no physical
   presence, so a physical label is meaningless — but it still has a number, and
   hiding the setting for those devices is a UI decision with no obvious right
   answer. Currently the setting is offered and simply does nothing useful.
5. **Should the wallpaper carry anything besides the name and the number?** A
   cluster name, a tag, a QR code of the `stableId` that a phone camera could
   scan to open the device page. Each is defensible; each is also how a clean
   black label becomes a dashboard nobody can read from a metre away. The
   owner's specification is two lines, and this plan builds exactly two lines.
6. **Is `label` still the right default for the name?** With a number present,
   the model name adds little on a fleet of twenty identical phones — an
   operator may prefer the default label to be empty and the wallpaper to show
   the number alone. §3.3 keeps today's behaviour; changing it is a one-line
   edit to `admission.ts:109` once someone decides.
