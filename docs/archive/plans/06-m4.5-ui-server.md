# Plan 06 — M4.5 : ui-server (Persistent On-Device Inspector)

> Status: implemented — persistent on-device `ui-server` inspector (am instrument launcher, JSONRPC client, watchdog, setText/longClick/doubleClick) shipped
> Ships: packages/drivers/src/inspector/ui-server/index.ts
> **Depends on:** Plan 01–05 selesai (device registry + stableId, Toolchain Manager, session/lease/queue, script framework + inspector `uiautomator-dump` sudah jalan — plan ini adalah upgrade path-nya).
> **Referensi spec:** §7.4 (inspector persistent on-device), §7.1–§7.3 (engine & toolchain), §9.5 (capability locks), §16 (NFR: inspector query < 200 ms per find), §20 baris M4.5, §21 (sumber riset openatx/uiautomator2).

---

## 1. Goals

Setelah plan ini selesai, semua poin berikut TRUE dan terukur:

- Ada engine Inspector baru `ui-server` di `packages/drivers` yang mengimplementasikan interface `Inspector` (spec §7): `dump()`, `find(sel)`, `screenshot()` — query selector dieksekusi **di device**, bukan parse dump di host.
- Engine `ui-server` juga menyediakan aksi elemen langsung `set_text`, `long_click`, `double_click` (spec §7.4) lewat capability opsional, tanpa mengubah signature `Inspector` untuk engine lain.
- APK server (app APK + test APK) dikelola oleh Toolchain Manager sebagai tool entry `ui-server` (`swappable: false`, checksum sha256, versi ikut core — spec §7.2/§7.3).
- Lifecycle lengkap: install otomatis saat pertama dipakai → start via `adb shell am instrument` saat `DeviceSession` dibuat dengan `inspection: 'ui-server'` → health check HTTP ping → **auto-restart** (watchdog) kalau instrumentation di-kill sistem → stop + cleanup (kill instrumentation, lepas `adb forward`) saat session release.
- Port di host dialokasikan per device dari range terkonfigurasi lewat `PortAllocator` (registry in-memory, tidak pernah bentrok antar 10+ device di satu host).
- `waitFor` di runner memakai polling interval pendek (default 80 ms, configurable 50–100 ms) ketika inspector aktif = `ui-server`.
- **NFR terverifikasi:** benchmark script menunjukkan `find()` p95 < 200 ms (target spec §16) pada minimal 1 device fisik uji, dan hasilnya jauh lebih cepat dari `uiautomator-dump` pada device yang sama.
- Default `devices.inspection` berubah menjadi `'ui-server'`; `uiautomator-dump` tetap terdaftar sebagai engine fallback, dengan kebijakan auto-fallback yang terdefinisi (lihat §3.5).
- **Script API tidak berubah sama sekali** — script dari Plan 05 (`waitFor`, `tap({id})`, `type`, dst.) jalan tanpa modifikasi di atas engine baru. Ini bukti abstraksi `Inspector` benar.
- Capability lock `['instrumentation']` untuk `ui-server` di-enforce oleh session manager (spec §9.5).
- `bun test` hijau; unit test baru untuk port allocator, selector mapping, JSONRPC client, watchdog state machine.

## 2. Non-goals

Sengaja TIDAK dikerjakan di plan ini:

- **Appium engine** (inspector/input) — opt-in, Plan 11 (M8). Termasuk inspeksi WebView/hybrid penuh (context switching, chromedriver): eksplisit di luar scope, lihat §3.7.
- **Build APK ui-server sendiri berbasis UiAutomator2 API** — keputusan default plan ini adalah vendorkan APK open-source openatx (lihat §3.2); membangun APK sendiri adalah opsi masa depan yang disiapkan lewat abstraksi, bukan dikerjakan sekarang.
- **scrcpy display/input** — Plan 08 (M6). Plan ini tidak menyentuh video/input path.
- **UI Studio untuk memilih inspector per device** — panel driver selection lengkap masuk Plan 07 (M5). Plan ini cukup lewat nilai `devices.inspection` di DB + API yang sudah ada dari Plan 01–05.
- **OCR/pixel inspector** (`ocr-pixel`, spec §7.1) — future.
- Perekaman/streaming hierarchy realtime ke Studio (inspector overlay UI) — future, bukan bagian M4.5.

## 3. Konteks & keputusan desain

### 3.1 Kenapa perlu (rekap spec §7.4)

`uiautomator dump` (Plan 05) = 0.5–2 detik per dump, gagal saat UI terus berubah ("could not get idle state"), dan `waitFor` yang polling di atasnya membuat script merayap. Solusi terverifikasi industri (openatx/uiautomator2, dipakai luas): **server instrumentation persistent di device** — sekali start, query berkali-kali via HTTP/JSONRPC lokal di device, di-forward ke host lewat `adb forward`. Selector dieksekusi di device oleh UiAutomator2 API → cepat, lebih tahan UI dinamis, dan bisa aksi elemen langsung (`set_text` jauh lebih reliable daripada inject keystroke, termasuk di field dalam WebView).

### 3.2 Keputusan: vendorkan APK openatx vs build APK sendiri

Dua opsi:

| Aspek | (a) Vendorkan `openatx/android-uiautomator-server` apa adanya | (b) Build APK sendiri (UiAutomator2 API + HTTP server minimal) |
|---|---|---|
| Kecepatan jadi | **Hari** — APK release siap pakai, protokol JSONRPC terdokumentasi de-facto, terbukti di lapangan bertahun-tahun | Minggu — butuh project Gradle/Android, CI build, debugging instrumentation dari nol |
| Maintenance | Bergantung upstream (aktivitas repo naik-turun); tapi kita pin 1 versi + checksum, tidak auto-update | Full kontrol; tapi nambah 1 codebase Java/Kotlin + toolchain Android ke repo yang sepenuhnya TS |
| Lisensi | MIT (openatx) — kompatibel redistribusi; **wajib diverifikasi ulang per file rilis sebelum jual** (masuk `LICENSES.md`, Plan 10) | Milik sendiri, bebas |
| Ukuran API | Lebih besar dari kebutuhan kita (banyak method tak terpakai) — tidak masalah, kita cuma panggil subset | Bisa minimal persis kebutuhan (dump/find/click/set_text) |
| Risiko protokol | Protokol JSONRPC upstream bisa berubah antar versi → mitigasi: pin versi + checksum via Toolchain Manager | Tidak ada |
| Kompatibilitas Android baru | Ikut upstream (kadang telat) | Kita yang kejar sendiri |

**Keputusan plan ini: mulai dari (a)** — vendorkan APK openatx versi tertentu yang kita test, dikelola Toolchain Manager (checksum, `swappable: false`, versi ikut core — perlakuan seperti scrcpy-server §7.6 karena protokol client↔server coupled). **Dengan abstraksi** supaya bisa pindah ke (b) tanpa menyentuh core/SDK:

- Engine `ui-server` di drivers hanya bergantung pada interface internal `UiServerClient` (JSONRPC method yang kita pakai) + `UiServerLauncher` (cara start/stop di device). Ganti APK = ganti implementasi dua interface ini, `Inspector` yang dilihat core tidak berubah.
- Subset JSONRPC yang boleh dipakai didokumentasikan eksplisit (§4.4) — dilarang memanggil method di luar subset itu, supaya surface migrasi ke APK sendiri kecil.

Keputusan final "kapan/apakah pindah ke (b)" = keputusan manusia → **Open questions §9**.

### 3.3 Pola start: `am instrument` (bukan `app_process`)

Dua cara menjalankan server di device: (1) `adb shell am instrument` menjalankan test-APK sebagai instrumentation (pola openatx: app APK + test APK), (2) `app_process` menjalankan dex langsung (pola scrcpy-server). Plan ini pakai **(1) `am instrument`** karena itu cara yang didukung APK openatx yang kita vendorkan dan satu-satunya cara resmi mengakses UiAutomator2 API (butuh instrumentation context). Konsekuensi yang harus ditangani: **instrumentation gampang di-kill** oleh sistem (low memory killer, battery optimization, user force-stop, atau tool lain yang merebut UiAutomation — termasuk `uiautomator dump`!) → wajib ada watchdog + auto-restart (§4.6).

### 3.4 Port & forwarding

- **Device side:** server openatx listen di port tetap **9008** di device (localhost device).
- **Host side:** tiap device dapat satu `localPort` dari range konfigurasi `ENKAKU_UI_SERVER_PORT_RANGE` (default `27100–27299`, cukup untuk ~200 device). Alokasi lewat `PortAllocator` (registry in-memory di core, satu instance): claim saat session start, release saat session stop; verifikasi port benar-benar bebas di OS (bind-test) sebelum dipakai.
- Forward: `adb -s <serial> forward tcp:<localPort> tcp:9008`. Cleanup: `adb -s <serial> forward --remove tcp:<localPort>`.
- Semua exec adb lewat per-device command queue + semaphore global dari Plan 01 (spec §10.4) — tidak ada panggilan adb liar.

### 3.5 Kebijakan default & fallback

- Default `devices.inspection` (kolom DB + factory default) berubah `'uiautomator-dump'` → `'ui-server'` untuk **device baru**. Device existing di-migrate ikut default baru (migration Drizzle), karena script API tidak berubah dan fallback otomatis ada. (Kalau ini dianggap terlalu agresif → lihat Open questions.)
- **Auto-fallback (kebijakan final plan ini):** saat `createSession` dengan `inspection: 'ui-server'`, kalau server gagal start/health setelah **2 attempt** (install ulang APK di attempt ke-2), session **tetap dibuat** dengan engine `uiautomator-dump`, plus:
  - event WS `device.inspector.fallback` (payload: deviceId, from, to, reason) → Studio bisa menampilkan warning;
  - entry log level `warn`;
  - kolom `devices.inspection` **tidak** diubah (fallback per-session, bukan permanen).
- Fallback **mid-session** (server mati saat job jalan dan watchdog gagal restart setelah retry): `find`/`waitFor` yang sedang berjalan otomatis dilayani `uiautomator-dump` untuk sisa session, event yang sama di-emit. Job tidak gagal hanya karena inspector pindah engine.

### 3.6 Capability locks (spec §9.5)

`uiServer.locks = ['instrumentation']`. Session manager (Plan 04) menolak merakit `DeviceSession` yang mengaktifkan dua engine dengan lock beririsan — nantinya `appium` inspector (`['instrumentation','input-injection']`, Plan 11) konflik dengan `ui-server`. Catatan penting yang sama-akarnya: `uiautomator dump` CLI **juga** merebut UiAutomation dan akan membunuh instrumentation ui-server — maka engine `uiautomator-dump` dan `ui-server` tidak boleh aktif bersamaan dalam satu session; transisi fallback harus stop ui-server dulu (atau ui-server memang sudah mati) sebelum dump pertama.

### 3.7 Kompatibilitas

- **Android:** target dukung API 21+ (Android 5.0+); matriks uji minimal plan ini = 1 device Android 10–15 (sesuai ketersediaan lab). UiAutomator2 API sendiri stabil di rentang ini; perilaku spesifik (izin instrumentation, battery optimization yang membunuh proses) berbeda per vendor (Xiaomi/Oppo agresif) → dicatat di README engine + mitigasi watchdog.
- **WebView/hybrid app:** ui-server melihat WebView sebatas yang diekspos accessibility tree (banyak elemen kelihatan sebagai node generic). `set_text` ke input field dalam WebView **lebih reliable** daripada inject keystroke — itu keuntungan nyata. Tapi inspeksi WebView penuh (DOM, context switching) = Appium opt-in, Plan 11. Batas ini ditulis di README engine supaya ekspektasi user benar.

### 4.2 Interface engine (TS)

```ts
// packages/drivers/src/inspectors/ui-server/index.ts
import type { Inspector, Selector, UiNode } from '@enkaku/sdk'

/** Aksi elemen langsung — capability opsional di atas Inspector (spec §7.4). */
export interface InspectorElementActions {
  setText(sel: Selector, text: string): Promise<void>
  longClick(sel: Selector): Promise<void>
  doubleClick(sel: Selector): Promise<void>
}

export function supportsElementActions(
  i: Inspector,
): i is Inspector & InspectorElementActions {
  return 'setText' in i && 'longClick' in i && 'doubleClick' in i
}

export interface UiServerInspectorOptions {
  serial: string                    // alamat transport adb
  localPort: number                 // dari PortAllocator
  exec: (cmd: string) => Promise<string>  // per-device adb queue (Plan 01)
  findTimeoutMs?: number            // default 3000 (timeout satu call find)
  onStatus?: (s: UiServerStatus) => void  // → WS event device.inspector.status
}

export type UiServerStatus =
  | { state: 'starting' }
  | { state: 'healthy'; pid?: number }
  | { state: 'restarting'; attempt: number; reason: string }
  | { state: 'dead'; reason: string }       // watchdog menyerah → trigger fallback

export class UiServerInspector implements Inspector, InspectorElementActions {
  readonly id = 'ui-server'
  /** Hint untuk waitFor runner: query murah → poll rapat. */
  readonly recommendedPollIntervalMs = 80
  // dump()/find()/screenshot()/setText()/longClick()/doubleClick() — lihat §4.4
}
```

Runner `waitFor` (Plan 05) diubah minimal: interval polling diambil dari `inspector.recommendedPollIntervalMs ?? 500` (engine dump tetap 500 ms) dan bisa di-override `DeviceSettings`. `device.type(...)` di SDK: kalau ada elemen ter-target (call `type` didahului `waitFor({id})` pada input) SDK **tidak berubah** — internal `DeviceSession` yang memutuskan pakai `setText` bila engine mendukung dan selector target diketahui; selain itu jatuh ke InputSink seperti sebelumnya.

### 4.4 Protokol ke server (subset yang boleh dipakai)

`UiServerClient` hanya boleh memakai endpoint/method berikut (surface migrasi ke APK sendiri):

| Kebutuhan | Endpoint/method | Catatan |
|---|---|---|
| Health | `GET /ping` → `"pong"` | timeout 1 s |
| `dump()` | JSONRPC `dumpWindowHierarchy(compressed=false)` → XML string | parse dengan parser shared Plan 05 → `UiNode` |
| `find(sel)` | JSONRPC `objInfo(uiSelector)` (null/error = tidak ketemu) | dieksekusi di device |
| `screenshot()` | `GET /screenshot/0` → JPEG/PNG bytes | fallback: JSONRPC `takeScreenshot` |
| `setText` | JSONRPC `setText(uiSelector, text)` | clear dulu bila perlu (param method) |
| `longClick` | JSONRPC long-click by selector | |
| `doubleClick` | dua `click` cepat via JSONRPC bila tak ada method native | interval ~80 ms |

> Nama method persis **diverifikasi terhadap versi APK yang di-pin** pada langkah 5.2 (checklist khusus). Kalau ada gap (mis. tidak ada double-click native), implementasi komposit didokumentasikan di `client.ts`.

JSONRPC transport: `POST http://127.0.0.1:<localPort>/jsonrpc/0` body `{jsonrpc:'2.0', id, method, params}`; response di-parse Zod (konvensi §4.2 overview — tidak ada `as` casting).

### 4.6 Lifecycle & watchdog

State machine `watchdog.ts`:

```
idle → starting → healthy ⇄ restarting(n) → dead
```

- **starting:** launcher verifikasi APK terpasang (versi cocok via `dumpsys package` / checksum marker; kalau tidak → `adb install -r -g` dua APK dari path Toolchain Manager), lalu spawn `adb shell am instrument -w ...` sebagai proses background (stdout dipipe ke logger, prefix `ui-server:<deviceId>`), `adb forward`, lalu poll `/ping` tiap 250 ms sampai sukses (timeout start 15 s).
- **healthy:** ping tiap **5 s** saat session idle, **dinonaktifkan saat ada call aktif** (call yang sukses = health signal gratis; call gagal = trigger langsung).
- **restarting(n):** ping gagal 2× beruntun ATAU call error connection-refused → kill instrumentation (`am force-stop` package server + kill proses `am instrument` host-side), re-forward bila perlu, start ulang. Backoff 1 s / 3 s. Maks **2 attempt** per insiden.
- **dead:** menyerah → `onStatus({state:'dead'})` → session manager jalankan kebijakan fallback §3.5.
- **stop/cleanup (session release):** hentikan watchdog → kill instrumentation → `forward --remove` → `PortAllocator.release`. Idempotent; juga dipanggil dari lease-expiry force-release (Plan 04).

### 4.8 Tool entry Toolchain (Plan 02)

```ts
// packages/toolchain/manifests/ui-server.ts
export const uiServerManifest: ToolManifest = {
  id: 'ui-server',
  displayName: 'UI Server (on-device inspector)',
  swappable: false,               // versi ikut core, seperti scrcpy-server (spec §7.2)
  versions: [{
    version: '<pinned-upstream-version>',
    releasedAt: '<...>',
    compatibleCoreRange: '<semver core saat ini>',
    platforms: {
      // APK platform-independent terhadap HOST → satu key 'all'
      all: {
        url: 'https://github.com/openatx/android-uiautomator-server/releases/download/...app-uiautomator.apk',
        sha256: '<...>', sizeBytes: 0,
      },
    },
    // file kedua (test APK) → lihat langkah 5.1: manifest perlu dukung multi-file
  }],

```

Catatan desain: `ToolVersion.platforms` dari Plan 02 mengasumsikan 1 file per platform. ui-server butuh **2 file** (app APK + test APK). Solusi minimal-invasif: tambah field opsional `files?: { name, url, sha256, sizeBytes }[]` pada `ToolVersion` (backward-compatible; tool lama tidak berubah). Kalau Plan 02 ternyata sudah punya mekanisme multi-file, pakai itu (cek dulu di langkah 5.1). Key platform `all` berarti file yang sama untuk semua host OS.

First-run auto-provision (Plan 02) ditambah `ui-server` ke daftar tool wajib — kontribusi ke budget NFR "first-run < 90 s" kecil (2 APK ≈ beberapa MB).

## 6. Acceptance criteria

Semua harus lulus:

1. `GET /api/tools` memuat `ui-server` dengan `swappable:false`; install memverifikasi sha256 kedua APK; activate versi bebas ditolak.
2. `createSession({inspection:'ui-server'})` pada device uji: server terpasang & start otomatis, `/ping` sukses, `dump()`/`find()`/`screenshot()` jalan; query dieksekusi di device (dibuktikan: `find` tidak melakukan dump XML penuh di host — cek log/kode path).
3. `setText`, `longClick`, `doubleClick` berfungsi pada app sample (form input) via engine.
4. Script contoh Plan 05 jalan **tanpa perubahan satu baris pun** dengan `inspection:'ui-server'`.
5. `waitFor` polling ≤ 100 ms interval saat ui-server aktif (log/trace membuktikan interval efektif).
6. Benchmark: p95 `find()` < 200 ms (NFR §16) dan median lebih cepat minimal 3× dibanding `uiautomator-dump` di device yang sama.
7. Kill manual proses server di device → watchdog auto-restart, session tetap hidup, job tidak gagal.
8. Gagal start 2 attempt → auto-fallback ke `uiautomator-dump` + event `device.inspector.fallback`; `devices.inspection` di DB tidak berubah.
9. Session release / lease expiry → instrumentation mati, `adb forward` bersih, port dikembalikan (claim ulang device yang sama dapat port valid).
10. Dua device paralel dapat `localPort` berbeda; simulasi 200+ claim → `PORT_RANGE_EXHAUSTED` yang rapi, bukan bentrok.
11. Lock conflict: mencoba merakit session dengan dua engine ber-lock `instrumentation` → ditolak `LOCK_CONFLICT`.
12. `bun test` hijau seluruh workspace; tidak ada `any`/TODO baru tak beralasan; README ter-update (DoD global overview §7).

### 7.3 Benchmark NFR (`scripts/bench-inspector.ts`)

Metodologi terdefinisi supaya angka NFR bisa direproduksi:

- Buka app deterministik (Settings) via `am start`, tunggu idle.
- **Warm-up** 5 call (tidak dihitung).
- **N = 50** iterasi `find({text:'…'})` (target yang selalu ada) + 50 iterasi target yang tidak ada (worst case selector miss), ukur wall-time per call di host (termasuk hop adb forward — itu yang dirasakan script).
- Jalankan untuk kedua engine (`ui-server`, `uiautomator-dump`) di device yang sama, back-to-back.
- Output: p50/p95/max per engine + rasio; exit code ≠ 0 kalau p95 ui-server ≥ 200 ms → bisa dipakai di CI berlabel device.

```bash
ENKAKU_TEST_DEVICE=1 bun scripts/bench-inspector.ts --serial <serial>
```

Acceptance: p95 `ui-server` find < 200 ms (kedua kasus hit & miss); dicatat device + versi Android yang dipakai mengukur.

## 8. Risiko & mitigasi

| Risiko | Dampak | Mitigasi |
|---|---|---|
| Instrumentation di-kill sistem (LMK, battery optimization vendor, force-stop) | Query gagal mendadak di tengah job | Watchdog + auto-restart (§4.6); call yang gagal di-retry sekali setelah restart; terakhir fallback engine (§3.5). Dokumentasikan whitelist battery-optimization di README enrollment |
| `uiautomator dump` / tool lain merebut UiAutomation → server mati | Konflik diam-diam | Locks `instrumentation` + aturan §3.6 (dump & ui-server tak pernah aktif bersamaan dalam satu session); watchdog menangkap sisanya |
| Protokol JSONRPC upstream berubah antar versi | Engine rusak setelah bump versi | Pin versi + checksum via Toolchain (`swappable:false`), subset method terdokumentasi (§4.4), checklist verifikasi protokol di Tahap 3 tiap bump |
| Upstream openatx tidak aktif / rilis berhenti | Buntu di Android masa depan | Abstraksi `UiServerClient`/`UiServerLauncher` (§3.2) → jalur pindah ke APK sendiri tanpa sentuh core/SDK; keputusan di Open questions |
| Port bentrok dengan proses lain di host | Session gagal start misterius | Bind-test saat claim + range khusus terkonfigurasi + crash-recovery bersihkan forward sisa |
| Latency > 200 ms di device low-end / UI sangat dinamis | NFR gagal | Benchmark memisahkan hit/miss; kalau miss-case lambat, turunkan `waitForSelectorTimeout` sisi server (param JSONRPC `configurator` bila tersedia — cek Tahap 3); dokumentasikan device minimum |
| Install 2 APK gagal di ROM tertentu (izin `-g`, verifikasi paket) | Enrollment engine gagal | Attempt ke-2 install ulang; fallback policy menjamin session tetap jadi; error message actionable di event fallback |
| Lisensi/redistribusi APK upstream | Blocker jual | MIT (verifikasi per rilis) — audit final masuk `LICENSES.md` Plan 10; URL sumber + checksum dicatat di manifest |

## 9. Open questions

1. **Keputusan final (a) vs (b) (§3.2):** plan ini mulai dari vendorkan APK openatx. Kapan (dan apakah) pindah ke APK milik sendiri berbasis UiAutomator2 API — trigger-nya apa (upstream mati? butuh fitur custom? audit lisensi sebelum jual)? Butuh keputusan manusia; abstraksi sudah disiapkan.
2. **Versi upstream yang di-pin + checksum:** angka konkret diisi saat implementasi Tahap 1 setelah verifikasi rilis & lisensi file — perlu approval sebelum commit manifest.
3. **Migrasi device existing:** plan ini memigrasi `devices.inspection` row lama ke `ui-server` (karena ada auto-fallback). Alternatif konservatif: hanya device baru yang dapat default baru. Konfirmasi pilihan.
4. **`adb forward tcp:0`** (adb yang memilih port bebas) bisa menggantikan PortAllocator range-based dan menghilangkan risiko bentrok sepenuhnya — tapi port jadi tak dapat diprediksi (menyulitkan firewall rule & debugging). Plan ini pakai range+registry sesuai arahan; layak ditinjau ulang kalau operasional membuktikan sebaliknya.
5. **Ekspos `long_click`/`double_click` di SDK script API:** spec §7.4 menyebut aksi ini di level engine, tapi spec §11 tidak mendefinisikan `device.longClick()` di API script. Plan ini mengimplementasikan di engine + `DeviceSession` internal saja (script API tidak berubah). Apakah SDK perlu method publiknya (minor version bump `@enkaku/sdk`)? Butuh keputusan produk.
6. **Interaksi dengan input mode saat WebView `set_text`:** kalau nanti (M6) input default `scrcpy-uhid` aktif bersamaan, `set_text` via instrumentation "melewati" jalur hardware-like — untuk QA detection-testing ini bisa mengubah karakteristik input yang diuji. Perlukah flag per-script/per-device "paksa type via InputSink"? (Relevan baru di Plan 08+, catat di sini karena akarnya di engine ini.)
7. **Health/status ui-server di UI Tools (Plan 07):** spec §7.7 punya `POST /api/tools/:id/check` — untuk ui-server, "health" itu per-device (server jalan di device), bukan per-binary di host. Definisi check yang benar (checksum file saja? atau status per-session?) diputuskan di Plan 07.
