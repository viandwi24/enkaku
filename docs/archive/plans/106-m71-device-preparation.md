## 1. Goals

1. **One state per on-device component**, not one for the guest agent and nothing for anything else (G1, G3).
2. **A failure names which component failed and why**, and is **retryable from the device popup** (G4, the owner's own ask).
3. **Adding a future component is a registry entry**, not a new subsystem — the owner's stated reason for wanting this shape at all.
4. The Wall says a device is not fully prepared, without a chip per component (G5).

## 2. Non-goals

- **Not auto-building the guest agent APK** (G7) — the three-tier resolution stands unchanged.
- Not replacing `transfer.ts`'s install path (G6); the state machine drives it, it does not reimplement it.
- Not blocking a device from use while preparing. A phone with a failed guest agent still streams and still runs scripts that do not need the agent; preparation is a readiness signal, never a gate, unless a specific component says otherwise.

## 3. Context and design decisions

### 3.1 Generalise the state that already exists, do not invent a second one

G1/G2: `AgentState` already has the right vocabulary — `absent`, `provisioning`, `ready`, `outdated`, `failed`, `unsupported` — and the provisioner already carries attempts, a next-attempt time, a reason string, and a bounded backoff.

So the model is **that shape, keyed by component**, not a new one beside it:

```
devices.preparation: {
  [componentId]: {
    state, version?, reason?, attempts, nextAttemptAt, checkedAt
  }
}
```

The guest agent becomes the first entry rather than a special case. Its own column can remain as a derived read for compatibility, or be migrated — decide it in the step, and if it stays, say which is authoritative so two fields cannot disagree.

### 3.2 A registry, so a future component is an entry

The owner's reason for asking: *"untuk fitur selanjutnya jika ada apk yang diperlukan juga bisa enak tinggal tambah aja di proses state ini."*

So each component declares itself: an id, how to detect its presence and version on a device, how to install it, whether a device can be considered prepared without it, and whether it is even applicable (an SDK level below the guest agent's minimum makes it `unsupported`, not `failed` — G1's vocabulary already distinguishes these, and that distinction is exactly what stops an old phone reporting a permanent error).

**`scrcpy-server` is the test of whether the registry is honest** (G3): it is pushed fresh every session and deletes itself, so its "installed state" is meaningless. Either it is not a registry entry, or the registry has to express "verified at use, not installed" — and that is worth deciding deliberately rather than forcing a per-session artifact into an install-once model.

### 3.3 Retry belongs to the operator, because the automatic one is bounded on purpose

G4 is the shape to avoid repeating: three attempts, then `nextAttemptAt: null`, persisted across restarts, invisible.

The bound itself is right — twenty phones with a bad APK path must not produce an install storm. What was missing is that **the operator could not see it or act on it**. So: each component's state is visible in the device popup, with its reason, and a Retry that clears the bound for that component on that device.

§96.25's other lesson applies too: a core-side error (`E_ADB_UNAVAILABLE` — us, not the phone) must not consume the device's attempt budget. Any generalised runner inherits that rule, not just the guest agent's own path.

### 3.4 One signal on the Wall, not one per component

G5: a device that streams fine can still be broken. Plan 101 folded the agent alert into `.status-rail`'s colour precisely to avoid a chip per component on a wall of forty phones.

Preparation keeps that: the rail says *something* is wrong; the popup says *what*. Do not add a second per-tile indicator — the reason plan 90 §5 step 90.6 made the old chip quiet for healthy devices was that twenty healthy phones must not grow twenty chips, and that reasoning survives this plan unchanged.

### 3.5 When it runs

On admission (a new device), on reconnect, and on demand. Not on a timer — the same rule plan 89 §3.7 settled for labelling, and for the same reason: a poll loop over a rack is a cost paid forever to catch a rare change.

§96.25's boot-ordering lesson is a hard prerequisite: **nothing may run before the adb subsystem is ready**, or the first pass burns its budget on our own startup race.

### 106.7 — Preparation-in-progress is visible while it is running, not only once it settles

The owner's own follow-up, verbatim: *"bisa ngga kalau preparation lagi diinstall itu ada loadingnya di screen castingnya? terus di popupnya juga ada gitu entah ditaruh dimana progress installing preparationnya?"* Two surfaces: an overlay on the device popup's screen panel while a component is `provisioning`, and a live indicator plus elapsed time on that component's row in `PreparationPanel`.

**The constraint that decided what could honestly be built: `devices.preparation[componentId].state` never actually became `'provisioning'`.** `PreparationStateSchema`'s own doc comment (`packages/protocol/src/device-preparation.ts`) has said *"`provisioning` — a pass is in flight right now"* since 106.1, but neither `preparation/runner.ts`'s `ensureComponentImpl` nor `agent-provisioner.ts`'s `ensureImpl` ever wrote that value — both go straight from reading `prior` to awaiting `component.run(row)`/`runOnePass(...)`, and only write once the pass resolves to a FINAL state (`ready`/`outdated`/`failed`/`unsupported`). On the owner's own phone, a failing `ui-server` install took 45.2s before returning — 45 seconds during which `GET /:id/preparation` and every `device.preparation` event were silent, because there was nothing anywhere recording that a pass was even running. This is a pre-existing gap (present since 106.1/106.2, inherited from `AgentState`, not introduced by this step) that this step closes — the two Studio surfaces could not be built honestly without it.

**Byte-level progress is impossible and was not attempted (§2, "never invent progress that isn't real")**: `ui-server-component.ts` installs through one opaque `hostAdb(['install', …])` CLI call with no `onProgress`; `agent-provisioner.ts`'s own `runOnePass` has no tick either. Both surfaces show an indeterminate spinner plus elapsed time only — never a percentage bar. `ComponentRow`'s own comment in `PreparationPanel.tsx` and `LiveView.tsx`'s own comment on its `provisioning` prop both state this plainly, so a future pass does not "improve" it into a fake number.

**The fix, scoped as narrowly as the two facts above allow — an in-memory, read-time-only overlay, never a persisted intermediate state:**

- `packages/core/src/device/preparation/runner.ts` and `packages/core/src/device/agent-provisioner.ts` each gained a `runningSince` map (in-memory, `Map<string, number>`), set to the pass's start time (unix seconds) immediately before `component.run(row)`/`runOnePass(...)` is awaited, and cleared in a `finally` on every exit path — success, a translated `failed` result, or the `E_ADB_UNAVAILABLE` defer's early return. Exposed as a new `runningSince(deviceId)` method on both `PreparationRunner` and `AgentProvisioner`.
- **Deliberately NOT written to `devices.preparation`, and never routed through `maybeRecordTransition`'s event contract.** Two reasons, both load-bearing: (1) persisting an intermediate `'provisioning'` row would have to be REVERTED on an `E_ADB_UNAVAILABLE` defer (or left permanently stale on a core crash mid-install) — exactly the "two writers, one fact" and "stale row" hazards 106.5's whole migration exists to avoid; (2) it would double the event count every existing transition test in `runner.test.ts`/`agent-provisioner.test.ts` asserts (`expect(events).toHaveLength(1)` for a single settled pass) — a test-visible, deliberately-avoided behavioural change to code §96.25 and 106.2/106.5 were careful to keep stable. `runningSince`'s own doc comment on both interfaces states this reasoning, so it is not rediscovered and "fixed" into a persisted write later.
- `packages/core/src/api/device-preparation.ts`'s `GET /:id/preparation` overlays this onto the persisted record at READ time only: a component with a live `runningSince` entry renders `state: 'provisioning'`, `checkedAt: <start time>` in the HTTP response, while the DB itself never saw that value. The overlay reverts to whatever the last COMPLETED pass decided the instant `runningSince` clears — proven directly in `device-preparation.test.ts`'s new "never persisted" test, which asserts the DB row stays untouched while the overlay is live. The guest agent's own bridge (`agentProvisioner.runningSince`, wired the same optional-dependency way `ensure`/`status`/`remove` already are) is folded in alongside the registry components, so one endpoint covers both engines as it already did for `ensure`/`retry`.
- Six new core tests (`runner.test.ts` ×2, `agent-provisioner.test.ts` ×2, `device-preparation.test.ts` ×2) prove: a pending pass reports `runningSince`, an `E_ADB_UNAVAILABLE` defer clears it rather than leaving it stuck, it never leaks across devices, and the GET overlay is read-time-only.

**Why polling, stated so it is not silently "fixed" into a bare WS subscription**: there is a real event for a pass FINISHING (`device.preparation`/`device.agent`, already in `MAIN_EVENT_KINDS` since 106.1/90) but, by the design above, deliberately none for one STARTING — that fact lives only in the in-memory `runningSince` map, which nothing broadcasts. `packages/studio/src/lib/use-preparation.ts` (new, shared by both surfaces) polls `GET /:id/preparation` every 3s — the stated interval the brief asked for when live events are not available — and additionally refetches immediately on a `device.preparation`/`device.agent` WS event for the same device, so a genuine completion is not left waiting on the next poll tick. This is the literal "driven by the same transition events… if available; if not, poll at a stated interval" the brief asked for: completion is event-driven, start-detection is polled, and the hook's own doc comment says why rather than leaving the split to be reverse-engineered.

**Surface 1 — the screen panel (`LiveView.tsx`, a new optional `provisioning` prop, set only by `DevicePopup.tsx`'s screen panel).** A small, non-blocking pill (`pointer-events-none`, `absolute inset-x-0 bottom-0`, translucent `bg-bg/85`) reading "Installing UI server (openatx) · 12s" — never `LiveView`'s existing wake-panel treatment (`bg-bg/95` covering the whole area, disabling the canvas), because plan 106 §2 makes preparation a readiness signal, never a gate: the phone streams fine while a component installs, and an operator may be watching for exactly that reason. Names the component (the owner's own original ask — "mana apk yang gagal", extended here to "which one is running"), via `componentLabel` exported from `PreparationPanel.tsx` so the two surfaces cannot drift onto two different names for the same id. Disappears the instant nothing is `provisioning` any more, including when a component lands on `failed` — deliberately: `provisioningComponentFor` (`DevicePopup.tsx`, exported and unit-tested) only ever returns a component whose state IS `provisioning`, so a failure is never restated as a multi-line adb error over the video; the overlay vanishing is what points an operator at Settings › Preparation, which is where the reason actually lives. More than one component can theoretically be `provisioning` at once (the guest agent's own engine and the registry's `ensureAll` sweep are independent and can overlap) — the overlay has room for one line, so `provisioningComponentFor` picks the guest agent first (deterministic, not whichever happened to resolve first in `Object.entries`), documented in its own comment.

- [ ] Every component's state uses one shape; no component has a field the others lack (H1). **The shape is unified by construction** (`PreparationComponentStatusSchema`, one definition, no per-component variant) and `runner.test.ts` exercises it against a synthetic SDK-gated component to prove `unsupported` works generically, not only for the one entry (`ui-server`) that ships today. As of 106.5, the guest agent's five state-machine facts (`state`/`version`/`reason`/`attempts`/`nextAttemptAt`/`checkedAt`) fit the SAME shape with no extra field — `devices.preparation['guest-agent']` is a plain `PreparationComponentStatusSchema` value like any other. What does NOT fully fit is EXECUTION: guest agent needs a live `hello()` handshake and identity facts (`appVersion`/`versionCode`/`androidSdkInt`/`capabilities`) the generic `PreparationComponent.run()` contract has no room for, so it keeps its own specialised engine rather than being registered in `preparation/registry.ts` (106.5's own status note has the full reasoning). Left unticked because H1 is an owner-run review (§7) of the four originally-envisioned entries, and the storage-vs-execution split this pass found is exactly the kind of thing that review should weigh in on — is a real, different engine per protocol-speaking component an acceptable shape for the registry, or a sign it needs an optional "identity" extension point? `scrcpy-server` was decided OUT (106.1).
- [x] A failed component names itself and its reason in the popup, and Retry clears that component's bound (§3.3). **Both halves done as of this pass.** The clearing half was done and tested since 106.5 for every component, including the guest agent (`POST /:id/preparation/:componentId/retry`, `api/device-preparation.test.ts`; bridged, not registered — see 106.5's status note — but the SAME endpoint works for it). The popup half (106.3, this pass): `PreparationPanel.tsx`, `SettingsPopup`'s tenth section — every component the endpoint can report gets a row, its own state/reason/version, and a Retry that clears only that component's bound; `PreparationPanel.test.tsx`.
- [x] A core-side error does not consume a device's attempt budget (§3.3, §96.25). `runner.test.ts` — `E_ADB_UNAVAILABLE` deferral: no write, no attempt consumed, no event.
- [x] Nothing runs before the adb subsystem is ready (§3.5, §96.25). `daemon-wiring.test.ts`'s new assertion: the preparation runner's boot sweep is anchored strictly after the `adb subsystem ready` log line, never before.
- [x] The Wall gains no new per-tile indicator (§3.4). True by construction, and no longer trivially so: 106.4 (this pass) confirmed `WallTile.tsx`'s existing `data-agent-alert` already reflects `devices.preparation['guest-agent']` (via 106.5's migration) with zero code change needed — the rail was already "folded into the existing signal" the moment 106.5 landed. Named, not claimed complete: this covers the guest agent only — `ui-server` and any future registry component has no farm-wide signal, since `DeviceInfo` carries no summary field for the full `devices.preparation` record and adding one is a `packages/core/**` change out of this pass's scope (the identical gap plan 107 step 107.4 already found for its own operation tray). See 106.4's own status note.
- [x] The guest agent APK is still never auto-built; its three-tier resolution is unchanged (G7). Untouched by this pass; `agent-provisioner.ts`'s only change is the behaviour-preserving `bounded-retry.ts` extraction (its own 30 pre-existing tests pass unchanged).
- [x] `unsupported` is distinguishable from `failed` — an old phone is not reported as broken (§3.2). `runner.test.ts` — an inapplicable component resolves `unsupported`, `run()` is never even called, no attempt is spent.
- [x] A device with a failed component still streams and still runs work that does not need it (§2). True by construction — the runner only ever writes `devices.preparation`; nothing in this pass's code touches `devices.status`, leases, quarantine, or the scheduler. Not separately verified against a live streaming session (no such test exists in this pass), so this is an architectural guarantee, not an end-to-end proof.

## 8. Risks and mitigations

- **A generalised runner repeats §96.25 at four times the scale.** Mitigated by §3.3/§3.5 carrying that hotfix's three fixes into the general path, and by 106.5 verifying they survived rather than assuming.
- **`scrcpy-server` forced into an install-once model it does not fit** (§3.2). Mitigated by deciding its membership explicitly in 106.1.
- **A chip per component on the Wall.** Mitigated by §3.4 and by plan 90 §5 step 90.6's own reasoning, which this plan does not get to re-litigate quietly.
- **Preparation becomes a gate**, blocking devices that would have worked. Mitigated by §2's rule: a readiness signal, never a gate, unless a component states otherwise.
- **Moving `ui-server`'s install onto the transfer machinery (106.8) silently drops its pre-existing `adb.maxInstallConcurrent` bound on an unattended boot-sweep code path** — found while verifying the move, not assumed safe. Mitigated by `preparationInstallSem` (106.8's own status note has the full account) restoring the same bound the old `hostAdb` lane already provided, read from the same farm-wide setting.

## 9. Open questions

1. **Is `scrcpy-server` a registry entry?** (§3.2.) It is verified at use and deletes itself; forcing it into "installed" may be a lie that looks tidy.

   **Decided in 106.1: no.** It is excluded entirely, not given a "verified at use" state within the shared schema either — adding a second vocabulary to `DevicePreparationSchema` for the sake of one component that already has a correct, different mechanism (`packages/scrcpy/src/session.ts` verifies and pushes it every session) would be complexity spent to paper over a non-gap. `packages/protocol/src/device-preparation.ts`'s own doc comment records this so a future reader does not "fix" the omission.

2. **Does `devices.agent` stay as a derived read, or get migrated away?** Two fields that can disagree is worse than either choice.

   **Decided in 106.1, executed in 106.5.** 106.1 kept `devices.agent` authoritative, unmigrated, through steps 106.1/106.2 (`devices.preparation` carried every component EXCEPT the guest agent, so the two columns could not disagree because there was nothing in the new column to disagree WITH). **106.5 completed the move**: `devices.preparation['guest-agent']` is now authoritative for `state`/`reason`/`checkedAt`/`attempts`/`nextAttemptAt`, and `devices.agent` is a derived/compat read — narrowed to `GuestAgentIdentitySchema` (`appVersion`/`versionCode`/`androidSdkInt`/`capabilities`, the facts a live `hello()` handshake learns that have no equivalent in the generic per-component shape), with no `state` field left to disagree with the new column about. Both are written together, atomically, from the same computed value, by one function (`agent-provisioner.ts`'s `writeCached`) — mirroring exactly how `DeviceInfo.agent` (the protocol-level chip on `GET /api/devices`) was already a derived read of `devices.agent` via `deriveAgentState`; that same function now reads the new authoritative column instead, through a shared helper (`device/preparation/guest-agent-status.ts`) so there is exactly one place either column is combined or, for a pre-migration row, bridged. Recorded in `packages/core/src/db/schema.ts`'s `agent`/`preparation` column comments, which is where a reader touching either column will actually see it.

3. **Should a device be admitted at all if a `requiredFor` component cannot install?** §2 says preparation is not a gate — but "required" implies otherwise for at least some component, and nobody has named which.

   **Not decided by this pass.** `PreparationComponent` (`packages/core/src/device/preparation/types.ts`) carries no `requiredFor`/gating field at all — 106.1/106.2 built only `ui-server`, which is not required for anything (a session already falls back to `uiautomator-dump` when it is absent), so the question never had to be answered to ship these two steps. Left open for whichever future step first registers a component that plausibly IS required.

4. **Does the Wall's rail need a farm-wide, all-component preparation signal, and if so, what shape?** Raised by 106.4 (this pass) and, independently, by plan 107 step 107.4 for its operation tray — the same underlying gap found twice from two different surfaces.

   **Not decided or built by this pass, deliberately.** `DeviceInfo` carries exactly one preparation-shaped field today (`agent`, the guest agent's own coarse state, riding the existing device list/WS broadcast) — every other registered component (`ui-server`, and whatever is registered after it) has no farm-wide-visible signal at all, so neither the Wall's rail nor 107's tray can show it without either a per-tile/per-entry fetch (the exact fan-out F27 already paid down once, forbidden for the same reason here) or a new `packages/core/**` field. This pass's own instructions scoped it to `packages/studio` only, so the shape of that field — a single worst-state-across-components enum, a bitmask, a list of failing component ids, something else — is intentionally left unspecified rather than guessed at and half-built. A future pass adding it should extend `DeviceInfo`/`deriveAgentState`'s neighbourhood in `registry/device-registry.ts`, compute it once server-side from `devices.preparation`, and let both the Wall (`WallTile.tsx`'s `data-agent-alert`, generalised) and the operation tray (`lib/operations.ts`) read the SAME field rather than inventing two.

   **106.7 (this pass) re-confirmed the same boundary for `provisioning` specifically**, and additionally decided the device POPUP's own screen-panel overlay is NOT the same gap: it renders once per open popup, not once per Wall tile, so it does not need the farm-wide field this question is about — see 106.7's own status note for the reasoning (`docs/design.md`'s "nothing that scales with device count" permits a bounded, once-per-popup cost the SAME rule forbids per-tile).

5. **Should preparation installs route through `runTransfer` instead of `hostAdb install`/the guest agent's own launcher?** Raised by 106.7, while building the honest ceiling for "is a component installing right now" (an indeterminate spinner plus elapsed time, no byte progress — see 106.7's own status note for why a percentage was not attempted).

   **Not decided or built by this pass — reported as a recommendation, not a ruling.** `POST /api/devices/:id/install` (G6, `packages/core/src/device/transfer.ts`) already has everything preparation's own progress question is missing: a staged push with a real `onProgress` byte callback, an operation id `transfer-registry.ts` tracks, and — for free, since plan 107 step 107.4 already named preparation as invisible to its own tray — an entry in the operation tray the moment a preparation install rode the same machinery. This is the ONE change that would answer the owner's question completely (a real percentage, not an honest-but-blunt spinner) and close 107.4's gap at the same time, which is exactly why it is worth recording even though this pass did not attempt it.

   The reason it was not attempted here: it is a real behavioural change to a path that currently works, not an observability addition like the rest of 106.7. `packages/core/src/device/preparation/ui-server-component.ts` and `agent-provisioner.ts`'s own launcher both install through ONE opaque `hostAdb(['install', …])`/`adb install` CLI call; `runTransfer` instead PUSHES the APK to a staged path and then runs `pm install` as a second step — different failure modes (a push that succeeds but an install that fails is a state `hostAdb install` cannot produce today), a different on-device footprint during the install (a staged file that must be cleaned up on every exit path, which `transfer.ts` already does but the preparation components do not need to, since they have no staging step at all), and a different concurrency story (`runTransfer` rides the transfer registry's own bookkeeping, not the bounded install lane `agent-provisioner.ts`/`preparation/runner.ts` already share via `hostAdb`'s `adb.maxInstallConcurrent`). Swapping the mechanism underneath `ui-server-component.ts`'s `run()` (and, more invasively, `agent-provisioner.ts`'s `runOnePass`, whose R1 forced-repair-then-re-hello recursion is not `runTransfer`-shaped at all) is exactly the kind of change that needs its own plan and its own owner-run verification (H2's "does a rack-wide pass storm adb" question would need re-asking under a different mechanism entirely), not a decision folded quietly into an observability step.

   Left for the owner to weigh: real byte progress and a tray entry, against rebuilding two working install paths (one of which — the guest agent's — has an R1 repair-then-rehello cycle §96.25 spent real effort getting right) on a different primitive.

   **Decided in step 106.8 (2026-08-17, owner explicitly approved): `ui-server` converted, the guest agent deliberately left as it was.** Not a half-measure done and gone quiet on the other half (this section's own opening instruction) — the guest agent's install stays on `createGuestAgentLauncher`'s own `hostAdb install` path specifically because of the R1 concern this paragraph already named: `ensureInstalled({ force: true })` is one internal leg of a live-`hello()`-triggered forced-repair-then-re-hello recursion (`runOnePass` calling itself once, plan 90 §3.9 rule 1) with no `runTransfer`-shaped equivalent, and rebuilding that on a different primitive is real, separate scope this step does not take on — recorded at the call site itself (`agent-provisioner.ts`, the comment directly above `launcher.ensureInstalled(...)` inside `runOnePass`), not only here. `ui-server` has no such recursion (`ui-server-component.ts`'s `run()` calls `ensureInstalled()` once, no force-repair loop), so it converted cleanly.

   The concurrency question this paragraph itself raised ("a different concurrency story... `runTransfer` rides the transfer registry's own bookkeeping, not the bounded install lane... via `hostAdb`'s `adb.maxInstallConcurrent`") turned out to be real, not hypothetical, and was fixed rather than left as a caveat: `installFromLocalApk`'s streaming lane genuinely has no farm-wide cap of its own (confirmed by reading `packages/adb/src/client.ts` directly), so 106.8 added `preparationInstallSem` (`daemon.ts`) — a semaphore scoped to preparation installs only, sized from the SAME `adb.maxInstallConcurrent` setting `hostAdb`'s own lane already reads — to restore H2's guarantee on this new code path rather than silently losing it. See 106.8's own status note for the full account, including exactly what stayed out of scope (an operator's own `POST /:id/install` had no comparable cap on this lane before this step either, and still does not — a separate, pre-existing condition, not something 106.8 was asked to fix everywhere).
